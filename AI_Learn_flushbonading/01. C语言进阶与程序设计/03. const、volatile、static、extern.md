## 三、系统知识讲解与代码分析

### 3.1 四个关键字的本质区别
`const`、`volatile`、`static`、`extern` 经常一起出现，但它们并不属于同一类概念。

| 关键字 | 所属类别 | 核心作用 | 典型应用 |
| --- | --- | --- | --- |
| `const` | 类型限定符 | 限制通过特定左值修改对象 | 只读参数、配置数据 |
| `volatile` | 类型限定符 | 约束编译器对对象访问的优化 | 硬件寄存器、中断标志 |
| `static` | 存储类说明符 | 影响存储期或链接属性 | 静态局部变量、模块私有变量 |
| `extern` | 存储类说明符 | 声明具有相应链接属性的标识符 | 多文件共享变量 |


#### 3.1.1 四个必须区分的概念
**1. 作用域（Scope）**

决定一个变量名在源代码中的哪些位置可见。

**2. 存储期（Storage Duration）**

决定一个对象在程序执行期间何时存在。

**3. 链接属性（Linkage）**

决定不同作用域或翻译单元中的同名声明是否指向同一个实体。

**4. 并发同步（Concurrency Synchronization）**

决定多个任务、中断或 CPU 核心同时访问共享数据时，能否满足正确性要求。

前三个是 C 语言对象和标识符的属性；第四个属于并发程序设计问题。

它们不能相互替代。

### 3.2 const：只读访问与类型限定
#### 3.2.1 const 的基本作用
```c
const uint32_t timeout_ms = 1000;
```

这表示不能直接修改 `timeout_ms`：

```c
timeout_ms = 2000; // 违反 const 限定
```

需要注意：

**const 不等于变量一定存放在 Flash，也不意味着底层数据绝对无法变化。**

它限制的是程序通过 const 限定的左值修改对象的行为。

例如：

```c
uint32_t value = 10;

const uint32_t *p = &value;

value = 20;     // 合法
// *p = 30;     // 不允许

uint32_t result = *p; // 20
```

原对象 `value` 并非 const 对象，因此仍然可以通过其他合法途径修改。

但如果对象本身定义为 const，再通过强制类型转换去修改它，则属于未定义行为。

#### 3.2.2 const 与指针
这一部分与 1.2《指针基础、二级指针、指针与数组》直接相关。

**第一种：指向 const 的指针**

```c
uint32_t a = 10;
uint32_t b = 20;

const uint32_t *p = &a;
```

含义：

+ 可以改变 p 指向哪里。
+ 不能通过 p 修改所指对象。

```c
p = &b;   // 合法
// *p = 5; // 不合法
```

**第二种：const 指针**

```c
uint32_t a = 10;

uint32_t *const p = &a;
```

含义：

+ p 自身不能再指向别处。
+ 可以通过 p 修改 a。

```c
*p = 20;  // 合法
// p = &b; // 不合法
```

**第三种：指向 const 的 const 指针**

```c
uint32_t a = 10;

const uint32_t *const p = &a;
```

含义：

+ p 不能指向其他对象。
+ 不能通过 p 修改所指对象。

#### 3.2.3 const 指针总结
| 声明 | 能修改指针指向吗？ | 能通过指针修改对象吗？ |
| --- | --- | --- |
| `uint32_t *p` | 能 | 能 |
| `const uint32_t *p` | 能 | 不能 |
| `uint32_t *const p` | 不能 | 能 |
| `const uint32_t *const p` | 不能 | 不能 |


注意：这里讨论的是通过当前指针的访问权限，不表示对象一定无法被其他途径修改。

#### 3.2.4 嵌入式工程中的 const 参数
例如编写一个发送函数：

```c
void uart_send(const uint8_t *data,
               uint32_t length);
```

这里 `data` 使用 `const`，表达的是：

**UART 发送函数不应该通过 data 修改调用者提供的缓冲区内容。**

这是一种接口契约。

但它不能保证调用期间其他任务不会修改该缓冲区，也不能自动解决 DMA 传输期间的缓冲区生命周期问题。

### 3.3 volatile：编译器优化与外部状态变化
#### 3.3.1 volatile 解决什么问题？
普通变量的读取可能被编译器优化、合并或重复利用。

但嵌入式系统中，一些对象的值可能被当前代码执行流程之外的机制改变，例如：

+ 硬件寄存器由外设自动更新。
+ 中断处理过程修改共享标志。
+ 某些设备访问具有特殊的读写副作用。

这时需要使用符合目标实现要求的 volatile 访问。

#### 3.3.2 STM32 中断标志示例
```c
#include <stdint.h>

static volatile uint8_t rx_done = 0;

void uart_rx_event(void)
{
    rx_done = 1;
}

int main(void)
{
    // 假设外设与中断已经初始化

    while (rx_done == 0)
    {
        // 等待接收完成
    }

    return 0;
}
```

对于典型嵌入式编译器和中断环境：

```c
static volatile uint8_t rx_done = 0;
```

能够使编译器按 volatile 对象的访问规则处理 `rx_done`。

如果移除 volatile：

```c
static uint8_t rx_done = 0;
```

编译器可能认为循环中没有改变这个普通变量的操作，从而优化掉某些重复读取。

实际是否优化成无限循环取决于完整程序和编译器，不保证所有工程都会出现相同现象。

#### 3.3.3 volatile 不是禁止全部优化
正确理解：

**volatile 约束针对 volatile 对象的访问，而不是让整个函数停止优化。**

它不提供以下保证：

+ 不保证复合操作的原子性。
+ 不保证多任务之间自动互斥。
+ 不保证普通内存访问都按预期排序。
+ 不提供跨 CPU 核心的通用同步机制。
+ 不解决 DMA 缓存一致性问题。

尤其在多核系统中，不能简单把 volatile 当成内存屏障使用。

#### 3.3.4 volatile 不保证 count++ 原子性
```c
volatile uint32_t count = 0;

void increment(void)
{
    count++;
}
```

`count++` 在逻辑上包含：

1. 读取 count。
2. 加 1。
3. 写回 count。

如果多个执行上下文同时修改，可能出现丢失更新。

所以：

```c
volatile uint32_t count;
```

不等于：

```text
线程安全的计数器
```

#### 3.3.5 volatile 与硬件寄存器
假设有一个符合目标 MCU 寄存器访问要求的地址：

```c
#define REG32(addr) \
    (*(volatile uint32_t *)(addr))
```

对于有效的可读写寄存器，可以进行：

```c
uint32_t value = REG32(REG_ADDR);
```

这里的 `REG_ADDR` 仅作为示意，实际地址必须由芯片参考手册确定。

硬件寄存器经常需要 volatile，因为寄存器内容可能由硬件自动改变。

但实际操作还必须考虑：

+ 寄存器允许的访问宽度。
+ 只读与只写属性。
+ 写 1 清零等特殊语义。
+ 读操作是否存在副作用。
+ 内存屏障及缓存要求。

volatile 本身无法解决所有硬件访问问题。

### 3.4 const volatile：软件只读，硬件可变
#### 3.4.1 为什么可以同时使用？
假设某个状态寄存器：

+ 软件只允许读取。
+ 硬件会更新其状态。
+ 软件需要反复检查寄存器数值。

适合使用：

```c
const volatile uint32_t *status_reg;
```

含义：

**const**：程序不能通过该指针修改所指对象。

**volatile**：读取所指对象时必须遵循 volatile 访问语义。

例如：

```c
uint32_t status = *status_reg;

// *status_reg = 1; // 不合法
```

#### 3.4.2 CMSIS 中的定义
ARM CMSIS 设备头文件中常见：

```c
#define __IM  volatile const
#define __OM  volatile
#define __IOM volatile
```

用于描述外设寄存器成员的访问属性。

示意：

```c
typedef struct
{
    __IM  uint32_t STATUS;
    __IOM uint32_t CONTROL;
} Device_TypeDef;
```

注意：

`__OM` 并不是通过 C 类型系统彻底禁止读取；真实寄存器的硬件访问限制仍需参照参考手册。

### 3.5 static：两个常见用途
static 的作用需要根据声明位置分析。

#### 3.5.1 static 局部变量
```c
uint32_t get_count(void)
{
    static uint32_t count = 0;

    count++;

    return count;
}
```

调用：

```c
uint32_t a = get_count(); // 1
uint32_t b = get_count(); // 2
uint32_t c = get_count(); // 3
```

这里：

+ `count` 具有块作用域。
+ `count` 没有链接属性。
+ `count` 具有静态存储期。
+ `count` 不会在每次函数返回后销毁。

对 C11 而言，静态存储期对象按静态初始化规则进行初始化，不应该照搬 C++ 局部静态变量首次执行到声明处才动态初始化的规则。

#### 3.5.2 static 文件作用域变量
```c
static uint32_t error_count = 0;
```

如果它定义在文件作用域：

+ 具有文件作用域。
+ 具有内部链接属性。
+ 具有静态存储期。

其他翻译单元不能通过这个名字直接访问该对象。

#### 3.5.3 static 文件作用域函数
```c
static void reset_driver(void)
{
    // 内部实现
}
```

此函数具有内部链接属性，不能作为普通的外部链接函数供其他源文件通过其名字调用。

适合将内部辅助函数隐藏在驱动模块中。

#### 3.5.4 两种 static 的区别
| 属性 | static 局部变量 | 文件作用域 static 变量 |
| --- | --- | --- |
| 作用域 | 块作用域 | 文件作用域 |
| 链接属性 | 无链接 | 内部链接 |
| 存储期 | 静态存储期 | 静态存储期 |
| 主要用途 | 保存局部状态 | 隐藏模块状态 |


#### 3.5.5 static 与实际内存布局
在典型 STM32、ESP32 工程中：

```c
static uint32_t count = 0;
static uint32_t threshold = 100;
static const uint32_t table[] = {1, 2, 3};
```

通常可能被安排到：

| 变量 | 常见段 |
| --- | --- |
| count | `.bss` |
| threshold | `.data` |
| table | `.rodata`，或被优化、重新安排 |


但 C 标准并不规定必须存在 `.bss`、`.data` 或 `.rodata` 这些段。

实际布局由编译器、链接器、链接脚本及优化共同决定。

**不要把 static 等同于“变量固定存放在静态缓冲区”。**

这部分将在 1.4 章节进一步研究。

### 3.6 extern：跨文件声明与链接
#### 3.6.1 extern 的基本作用
```c
extern uint32_t system_count;
```

表示声明一个对象，通常用于引用其他位置定义的同一个外部对象。

但 extern 并不自动创建该对象的存储定义。

#### 3.6.2 声明与定义
```c
extern uint32_t count;
```

通常是声明。

```c
uint32_t count = 0;
```

是定义。

而文件作用域：

```c
extern uint32_t count = 0;
```

因为带有初始化器，它也是定义，而不只是声明。

因此不要仅凭是否存在 extern，就判断一句代码是不是变量定义。

#### 3.6.3 多文件工程正确写法
**counter.h**

```c
#ifndef COUNTER_H
#define COUNTER_H

#include <stdint.h>

extern uint32_t count;

#endif
```

**counter.c**

```c
#include "counter.h"

uint32_t count = 0;
```

**main.c**

```c
#include "counter.h"

void app_test(void)
{
    count++;
}
```

这样，多个翻译单元引用的是同一个外部对象。

#### 3.6.4 多文件共享不代表必须使用 extern 变量
对于驱动内部状态，更推荐：

**counter.h**

```c
#ifndef COUNTER_H
#define COUNTER_H

#include <stdint.h>

void counter_add(void);
uint32_t counter_get(void);

#endif
```

**counter.c**

```c
#include "counter.h"

static uint32_t count = 0;

void counter_add(void)
{
    count++;
}

uint32_t counter_get(void)
{
    return count;
}
```

**main.c**

```c
#include "counter.h"

void app_test(void)
{
    counter_add();

    uint32_t value = counter_get();
}
```

优点：

+ 限制外部模块直接修改内部数据。
+ 降低模块间耦合。
+ 方便以后增加锁、状态检查和日志。
+ 更容易进行单元测试和维护。

注意：以上是顺序调用示例；如果存在并发执行，仍需增加同步设计。

### 3.7 常见编译与链接错误
#### 3.7.1 multiple definition
错误头文件：

```c
// config.h
uint32_t timeout_ms = 1000;
```

若两个 `.c` 文件都包含它，就会各自生成一个外部定义。

最终链接通常报：

```text
multiple definition of `timeout_ms'
```

正确方式：

```c
// config.h
extern uint32_t timeout_ms;
```

```c
// config.c
#include "config.h"

uint32_t timeout_ms = 1000;
```

#### 3.7.2 undefined reference
```c
// config.h
extern uint32_t timeout_ms;
```

但整个工程中没有匹配的外部定义。

如果其他代码实际使用该变量，就可能报：

```text
undefined reference to `timeout_ms'
```

排查方向：

1. 是否真正定义了对象？
2. 定义是否写成了文件作用域 static？
3. 定义所在的 `.c` 文件是否参与构建？
4. 链接时是否包含正确的组件或目标文件？
5. 名称与类型声明是否保持一致？

#### 3.7.3 头文件中误用 static
错误示例：

```c
// counter.h
static uint32_t count = 0;
```

如果两个源文件都包含这个头文件：

```text
counter.c → 自己的 count
main.c    → 自己的 count
```

它们是两个独立对象。

所以使用 static 可能让 `multiple definition` 链接错误消失，但同时引入共享状态不一致的问题。

#### 3.7.4 头文件保护宏的作用
```c
#ifndef CONFIG_H
#define CONFIG_H

// declarations

#endif
```

防止同一个翻译单元重复包含头文件内容。

它无法防止多个独立翻译单元各自定义同名外部变量。

#### 3.7.5 关于暂定定义
在文件作用域：

```c
uint32_t count;
```

属于暂定定义（Tentative Definition）。

不能简单认为没有初始化器就只是 extern 声明。

将这类代码放到多个源文件共用的头文件中，仍然可能产生链接问题。

GCC 10 及以后的默认 `-fno-common` 行为更容易暴露这种错误。

### 3.8 综合使用：ESP32-S3 UART 接收计数器
#### 3.8.1 需求
假设有一个接收计数器：

+ UART ISR 更新计数。
+ 应用任务读取计数。
+ 应用任务可以清零计数。
+ ESP32-S3 可能运行双核 FreeRTOS。

原始代码：

```c
static volatile uint32_t rx_count = 0;

void uart_rx_callback(void)
{
    rx_count++;
}

uint32_t uart_get_rx_count(void)
{
    return rx_count;
}
```

这不是足够完整的并发安全设计。

原因：

+ `rx_count++` 并非必然原子。
+ 另一个任务可能同时读取或清零。
+ volatile 不提供跨核心互斥。

#### 3.8.2 任务上下文与 ISR 上下文区别
FreeRTOS 的互斥锁主要用于任务间互斥。

**不能在真正的 ISR 中使用阻塞式互斥锁 API。**

对于 ESP-IDF v5.5 的双核 FreeRTOS，可以针对很短的共享数据访问使用 `portMUX_TYPE` 自旋锁保护的临界区。

#### 3.8.3 ESP-IDF 临界区示例
下面示例假设计数更新函数从允许使用对应 FreeRTOS ISR 临界区 API 的中断上下文调用，读取和清零函数从任务上下文调用。

```c
#include <stdint.h>
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"

static uint32_t rx_count = 0;

static portMUX_TYPE rx_lock =
    portMUX_INITIALIZER_UNLOCKED;

/* 从适用的 ISR 上下文调用 */
void uart_rx_from_isr(void)
{
    taskENTER_CRITICAL_ISR(&rx_lock);

    rx_count++;

    taskEXIT_CRITICAL_ISR(&rx_lock);
}

/* 从任务上下文调用 */
uint32_t uart_get_rx_count(void)
{
    uint32_t value;

    taskENTER_CRITICAL(&rx_lock);

    value = rx_count;

    taskEXIT_CRITICAL(&rx_lock);

    return value;
}

/* 从任务上下文调用 */
void uart_reset_rx_count(void)
{
    taskENTER_CRITICAL(&rx_lock);

    rx_count = 0;

    taskEXIT_CRITICAL(&rx_lock);
}
```

代码要点：

1. `rx_count` 使用 static，保持模块内部状态。
2. ISR 和任务侧使用同一个锁保护共享数据。
3. ISR 与任务使用对应的临界区接口。
4. 共享数据访问代码保持短小。
5. 临界区内不执行阻塞操作。
6. 不能用普通 FreeRTOS 互斥锁替代 ISR 临界区。
7. 使用 ISR API 还需要遵守目标中断级别及 ESP-IDF 的相关限制。

因为所有访问均通过同步机制协调，此例无需另外通过 volatile 实现任务间同步。

注意：临界区保护的是读写操作的互斥；计数器清零与中断计数的业务先后顺序，仍需根据具体需求定义。`uint32_t` 长期累加也要考虑无符号回绕。

#### 3.8.4 什么时候用任务通知或队列？
如果 ISR 的目标只是告诉一个任务“数据接收完成”，未必需要共享计数器。

可以考虑：

+ ISR 通知处理任务。
+ 任务在自己的上下文更新业务计数。
+ 任务统一管理接收状态。

这种单一所有者方式通常更容易减少共享状态。

后续将在 FreeRTOS 章节系统学习任务通知、队列、互斥锁和 ISR 安全 API。

### 3.9 常见关键字组合
| 声明 | 含义 |
| --- | --- |
| `const uint8_t *p` | 通过 p 只读所指对象 |
| `uint8_t *const p = &x` | p 自身不可重新赋值 |
| `const volatile uint32_t *reg` | 只读访问具有 volatile 语义的对象 |
| `static uint32_t count`（块内） | 块作用域、静态存储期、无链接 |
| `static uint32_t count`（文件作用域） | 文件作用域、静态存储期、内部链接 |
| `static volatile uint8_t flag` | 静态存储期、内部链接的 volatile 对象 |
| `extern uint32_t count` | 通常用于声明外部对象 |
| `extern const uint32_t version` | 声明对外可见的 const 对象 |


特别注意：在 C 语言中，文件作用域的普通 `const` 定义并不会像 C++ 中常见的 const 全局对象那样默认具有内部链接属性。跨文件引用时，必须区分 C 与 C++ 的规则。

### 3.10 工程开发检查清单
编写 MCU 驱动时，可依次检查：

1. 变量是否真正需要对外公开？
2. 文件内部状态是否应使用 static？
3. 头文件中是否只提供合适的外部声明？
4. 是否在一个源文件中提供唯一的外部定义？
5. 局部 static 是否会被多任务共享？
6. 外设寄存器是否采用正确的 volatile 限定？
7. 只读函数参数是否可以使用 const？
8. volatile 对象是否还需要原子操作或同步？
9. ISR 是否误用了仅适用于任务的 API？
10. ESP32-S3 双核场景是否考虑跨核心访问？

### 3.11 核心总结
本章最重要的结论：

**① const 管访问权限。**

通过 const 限定的左值，不能直接修改所指对象。

**② volatile 管编译器访问语义。**

适用于部分硬件寄存器、中断共享标志等场景，但不能代替线程同步。

**③ static 管存储期或链接属性。**

函数内部 static 主要体现为静态存储期；文件作用域 static 主要用于内部链接和模块封装。

**④ extern 用于跨文件声明与链接。**

头文件通常提供声明，源文件负责定义。

**⑤ 作用域、存储期、链接属性不是一个概念。**

它们分别描述名字可见范围、对象存在时间、同名声明是否引用同一实体。

**⑥ 并发安全必须单独设计。**

不要指望 const、volatile 或 static 自动解决多任务和中断并发问题。

## 四、工程应用与常见陷阱

1. `const volatile uint32_t *` 适合通过该指针只读、硬件可能更新的寄存器；实际地址和访问权限以芯片手册为准。
2. 多任务/跨核对 static 计数器执行 ++，仍需按运行上下文使用原子操作、锁或单拥有者任务设计。
3. 避免在公共 .h 中定义普通外部变量或 static 全局数组，分别会引起重复定义或每翻译单元各一份状态。

## 五、个人易错点与复盘

### 5.1 个人易错点与复盘
本节根据本轮学习中的实际回答整理。

#### 5.1.1 易错点 1：混淆块作用域和文件作用域
此前把函数内的 static 局部变量描述为“在 calculate 文件内”。

正确理解：

```c
static uint32_t total;

void calculate(void)
{
    static uint32_t count;
}
```

`total`：

+ 文件作用域。
+ 内部链接。
+ 静态存储期。

`count`：

+ 块作用域。
+ 无链接。
+ 静态存储期。

**static 不会自动将局部变量提升为文件作用域变量。**

#### 5.1.2 易错点 2：把 static 等同于特定内存区
此前使用“定义在静态缓冲区”解释局部 static。

应改为：

**static 局部变量具有静态存储期。**

其实际存储位置由编译和链接过程决定。

#### 5.1.3 易错点 3：认为 volatile 可以完全防止优化
正确理解：

volatile 约束对被限定对象的访问，但并不关闭全部编译器优化。

同时也不能把 volatile 当作通用线程同步机制。

#### 5.1.4 易错点 4：认为使用 static 就实现线程安全
static 只能影响存储期或链接属性。

同一个模块的函数仍然可能被多个任务并发调用。

```c
static uint32_t count;

void increment(void)
{
    count++;
}
```

即使 count 不对其他文件公开，多个任务调用 increment() 仍可能发生共享数据竞争。

#### 5.1.5 易错点 5：所有共享变量都直接使用 extern
最初采用 extern 共享变量的修改方案是合法的。

但工程上应进一步考虑：

+ 是否真的需要暴露变量？
+ 是否可以通过 API 访问？
+ 是否需要限制修改入口？
+ 以后是否可能需要同步机制？

对于模块内部状态，优先考虑：

```text
static 内部对象 + 对外接口
```

#### 5.1.6 易错点 6：任务互斥锁与 ISR 同步混用
此前提出使用互斥锁保护 UART 接收计数器，方向正确，但需要先明确执行上下文。

+ 任务与任务：可根据场景选择互斥锁等机制。
+ ISR 与任务：使用支持中断上下文的同步方案。
+ ESP32-S3 双核：还需要考虑跨核心互斥。

**先判断调用代码运行在 ISR 还是任务上下文，再决定使用何种同步 API。**

**1.** 前者不能通过 p 写 *p，但可重定向 p；后者不能重定向 p，能通过 p 修改非 const 对象。
