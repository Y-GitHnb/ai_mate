## 三、系统知识讲解与代码分析

### 3.1 首先区分存储期、内存段与物理存储器
理解 C 语言内存布局时，必须区分三个概念。

| 概念 | 解决的问题 | 示例 |
| --- | --- | --- |
| 存储期 | 对象在什么时候存在 | 自动存储期、静态存储期 |
| 内存段 | 编译、链接时如何组织对象 | `.text`、`.data`、`.bss` |
| 物理存储器 | 数据实际存放在芯片哪里 | Flash、SRAM、PSRAM |


**存储期属于 C 语言规则，内存段属于常见工具链实现，Flash 和 SRAM 属于硬件。**

不能把三者看成同一个概念。

#### 3.1.1 C语言常见存储期
**自动存储期**

```c
void test(void)
{
    uint32_t count = 0;
    uint8_t buffer[256];
}
```

这些普通块作用域变量通常具有自动存储期。进入相应代码块时对象开始存在，离开代码块时其生命周期结束。

在典型 MCU 工程中，需要实际存储时通常利用栈空间，但编译器也可能使用寄存器或优化掉某些对象。

**静态存储期**

```c
uint32_t global_count = 0;

void test(void)
{
    static uint32_t count = 0;
}
```

`global_count` 和 `count` 都具有静态存储期，整个程序运行期间持续存在。

区别在于：

+ `global_count`：文件作用域，通常具有外部链接。
+ `count`：块作用域，无链接属性。

**分配存储期**

```c
uint8_t *p = malloc(256);
```

`malloc()` 成功后获得一块动态分配内存，直到通过相应方式释放为止。

`p` 这个指针变量自身仍遵循它的声明位置所对应的存储期。

### 3.2 STM32 常见程序存储布局
典型 STM32 GCC 裸机程序会使用以下区域：

| 区域 | 常见内容 | 运行时常见位置 |
| --- | --- | --- |
| `.isr_vector` | 中断向量表 | Flash |
| `.text` | 程序机器指令 | Flash |
| `.rodata` | 只读常量数据 | Flash |
| `.data` | 具有初始值的可写静态数据 | SRAM |
| `.bss` | 零初始化静态数据 | SRAM |
| Heap | 动态分配的内存 | SRAM |
| Stack | 函数调用与执行现场 | SRAM |


这些是典型情况，并非 C 标准强制的内存布局。

实际 STM32 芯片可能具有多个 SRAM Bank，也可能让某些函数或数据存放在特殊 RAM 区域。

#### 3.2.1 .text
通常保存机器指令：

```c
int add(int a, int b)
{
    return a + b;
}
```

函数的机器指令通常位于 `.text`。

函数执行时，CPU 运行相应指令，并不是把整个函数代码压入栈中。

#### 3.2.2 .data
```c
uint32_t timeout = 1000;
static uint32_t threshold = 200;
```

在典型 STM32 工程中，这些有非零初始化值的静态存储期对象通常安排在 `.data`。

`.data` 具有两个重要位置：

+ Flash：保存初始化内容。
+ SRAM：程序运行时实际读写变量。

程序启动时，将 Flash 中的初始内容复制到 SRAM。

#### 3.2.3 .bss
```c
uint32_t error_count;
static uint8_t rx_buffer[1024];
```

这些对象通常放在 `.bss`。

C 语言要求它们按照静态初始化规则获得初始零值；典型 STM32 启动代码通过将 `.bss` 对应 RAM 区域清零来实现。

`.bss` 通常不需要在固件映像中保存等量的零字节，但仍然占用实际 SRAM。

例如：

```c
static uint8_t rx_buffer[4096];
```

通常会增加约 4096 字节的 `.bss` RAM 占用。

#### 3.2.4 const 是否必然位于 Flash？
不一定。

```c
const uint32_t table[3] = {1, 2, 3};
```

如果它是文件作用域对象，典型工具链通常可能放入 `.rodata`，并安排在 Flash。

但 C 语言只规定 const 类型限定带来的访问限制，不保证对象一定存储在 Flash。

### 3.3 栈（Stack）的工作原理
#### 3.3.1 什么内容可能入栈？
典型内容包括：

1. 实际需要内存存储的自动局部变量。
2. 不能全部通过寄存器传递的函数参数。
3. 需要保存的 CPU 寄存器。
4. 函数调用现场和必要的临时数据。
5. 中断进入时保存的执行上下文。
6. RTOS 任务切换时需要保留的任务上下文。

但并不是每个局部变量一定入栈。

例如：

```c
int add(int a, int b)
{
    return a + b;
}
```

在典型 ARM Cortex-M 调用约定下，参数可能通过 R0、R1 传递，结果通过 R0 返回，整个函数可能不需要专门的局部栈空间。

#### 3.3.2 SP：栈指针
ARM Cortex-M 通常使用向低地址增长的满递减栈。

+ PUSH：SP 向低地址移动。
+ POP：SP 向高地址移动。
+ 分配函数栈空间：SP 通常减小。
+ 回收函数栈空间：SP 通常增大。

示例：

```z80
push {r4, lr}
sub sp, sp, #24
```

假设初始：

```text
SP = 0x20004000
```

第一步：

```text
PUSH R4、LR：2 × 4 = 8 字节

SP = 0x20003FF8
```

第二步：

```text
24 十进制 = 0x18

0x20003FF8 - 0x18 = 0x20003FE0
```

最终：

```text
SP = 0x20003FE0
```

这两条指令总共使 SP 向低地址移动 32 字节。

注意：具体函数栈帧的结构和大小由编译器、调用约定及优化决定。

#### 3.3.3 函数返回后栈内存会怎样？
```c
void process(void)
{
    uint8_t buffer[256];
}
```

假设 buffer 实际安排在栈上。

函数返回后：

+ buffer 对象生命周期结束。
+ 对应栈空间通常可供下一次调用复用。
+ RAM 中原有字节不保证被清零。
+ 不允许继续通过失效指针访问 buffer。

错误示例：

```c
uint8_t *get_buffer(void)
{
    uint8_t buffer[256];
    return buffer;  // 错误
}
```

返回局部数组地址会造成悬空指针。

### 3.4 堆（Heap）与 malloc/free
#### 3.4.1 动态内存分配
```c
#include <stdint.h>
#include <stdlib.h>

void process(void)
{
    uint8_t *p = malloc(256);

    if (p == NULL)
    {
        return;
    }

    // 使用 p 指向的动态内存

    free(p);
}
```

需要区分：

```text
p 指针变量本身：
通常位于栈或寄存器

p 指向的 256 字节：
由动态分配器管理，通常位于堆
```

**指针变量所在的内存区域，不等于指针指向的对象所在区域。**

#### 3.4.2 free() 的作用
```c
free(p);
```

将已分配的内存归还给相应动态分配器。

这不意味着：

+ 对应 RAM 物理消失。
+ RAM 内容立即清零。
+ 已释放的指针仍可以继续访问数据。

释放之后，不能再通过悬空指针解引用这块内存。

#### 3.4.3 内存泄漏
```c
void test(void)
{
    uint8_t *p = malloc(256);

    if (p == NULL)
        return;

    // 使用内存，但没有 free
}
```

如果没有保存其他有效引用，函数返回后就失去了释放这块内存的途径。

动态分配器仍认为它被占用，造成**内存泄漏（Memory Leak）**。

内存泄漏与以下问题不同：

| 问题 | 含义 |
| --- | --- |
| 内存泄漏 | 动态分配内存没有得到正确释放 |
| 栈溢出 | 栈使用超出了其有效范围 |
| 堆栈碰撞 | 堆与栈使用区域发生重叠 |
| 内存越界 | 读写超过对象的合法边界 |
| 整数溢出 | 整数运算结果超出相应类型范围 |


这些概念不能混用。

### 3.5 static 局部数组与普通局部数组
```c
void process(void)
{
    static uint8_t buffer_a[256];
    uint8_t buffer_b[256];
}
```

典型 STM32 工程中：

| 属性 | buffer_a | buffer_b |
| --- | --- | --- |
| 存储期 | 静态存储期 | 自动存储期 |
| 常见位置 | `.bss` | 栈 |
| 函数返回后 | 仍然存在 | 生命周期结束 |
| 多次调用 | 共用同一份对象 | 每次相应调用具有自己的自动对象 |


将普通局部数组改为 static 可能降低栈需求，但也有代价。

```c
void process_data(void)
{
    static uint8_t temp[2048];
}
```

优点：

+ 降低函数栈占用。
+ 数组在函数返回后仍存在。

代价：

+ 整个程序运行期间占用静态 RAM。
+ 多次调用共用同一个对象。
+ 多任务并发调用可能产生冲突。
+ 可能降低函数可重入性。

**不能把所有大局部数组都简单改成 static 作为通用解决方案。**

### 3.6 STM32 上电启动时的内存初始化
典型 STM32 Cortex-M GCC 工程的启动流程：

```text
MCU 复位
    ↓
从向量表取得初始 MSP 与复位入口
    ↓
进入 Reset_Handler
    ↓
初始化 .data
（Flash → SRAM）
    ↓
清零 .bss
    ↓
其他系统或运行库初始化
    ↓
进入 main()
```

部分启动文件的 `SystemInit()` 调用顺序有所不同，应以当前芯片的实际启动代码为准。

#### 3.6.1 .data 为什么需要复制？
```c
uint32_t timeout = 1000;
```

普通 SRAM 断电后不能保证保存原值。

为了让变量在程序启动时具有 1000 的初始值，固件映像中需要保存对应初始化内容。

启动代码将其从 Flash 复制到 RAM。

#### 3.6.2 .bss 为什么只需要清零？
```c
static uint8_t buffer[1024];
```

这类静态存储期零初始化对象的初始内容全部为零。

典型工程只需要知道 `.bss` 起止地址，启动时把该区域清零，不需要在 Flash 中保存同样大小的零数据。

### 3.7 STM32 链接脚本（.ld）
链接脚本决定输出段如何安排到 MCU 的存储区域中。

#### 3.7.1 MEMORY
例如，假设芯片具有 256 KB Flash、64 KB SRAM：

```plain
MEMORY
{
    FLASH (rx) : ORIGIN = 0x08000000, LENGTH = 256K
    RAM (xrw) : ORIGIN = 0x20000000, LENGTH = 64K
}
```

含义：

+ `ORIGIN`：区域起始地址。
+ `LENGTH`：区域容量。

实际芯片的地址和容量必须查阅对应型号的数据手册。

#### 3.7.2 SECTIONS
简化示例：

```plain
SECTIONS
{
    .text :
    {
        *(.text*)
    } > FLASH

    .rodata :
    {
        *(.rodata*)
    } > FLASH

    .data :
    {
        _sdata = .;
        *(.data*)
        _edata = .;
    } > RAM AT> FLASH

    _sidata = LOADADDR(.data);

    .bss (NOLOAD) :
    {
        _sbss = .;
        *(.bss*)
        _ebss = .;
    } > RAM
}
```

这是用于说明分段原则的简化片段，不是完整可替换的 STM32 链接脚本。

#### 3.7.3 VMA 与 LMA
对于 `.data`：

```plain
.data : { ... } > RAM AT> FLASH
```

含义：

+ **VMA（运行地址）**：对象运行时所在地址，通常在 RAM。
+ **LMA（加载地址）**：初始化数据在固件映像中的位置，通常在 Flash。

所以同一份 `.data` 初始化内容可能同时涉及 Flash 和 RAM。

#### 3.7.4 常见链接符号
| 符号 | 含义 |
| --- | --- |
| `_estack` | 初始主栈顶 |
| `_sidata` | `.data` 初始化内容加载地址 |
| `_sdata` | `.data` 运行起始地址 |
| `_edata` | `.data` 运行结束地址 |
| `_sbss` | `.bss` 起始地址 |
| `_ebss` | `.bss` 结束地址 |


具体符号名称取决于链接脚本和启动文件。

#### 3.7.5 _Min_Stack_Size 的真正含义
常见 STM32CubeIDE 链接脚本中：

```plain
_Min_Heap_Size  = 0x200;
_Min_Stack_Size = 0x400;
```

`0x400` 是 1024 字节。

但这通常是**链接阶段用于堆栈最低空间预留和容量检查的配置值**。

它不代表：

+ CPU 自动把栈限制在 1024 字节。
+ 函数使用超过 1024 字节一定立刻 HardFault。
+ 链接成功就能够保证运行时没有栈溢出。

实际栈安全还依赖 RAM 布局、调用关系、运行时分配和硬件保护机制。

### 3.8 Map 文件、SU 文件与调试器
这是本章工程实践的重点。

#### 3.8.1 Map 文件
Map 文件是链接器生成的内存映射报告。

GCC 链接选项示例：

```text
-Wl,-Map=project.map
```

它可以帮助查看：

+ `.text`、`.data`、`.bss` 大小。
+ 静态对象的链接地址。
+ 各输出段的内存分配位置。
+ Flash、RAM 静态使用情况。

示例：

```text
.data  0x20000000  0x200
       load address 0x08003000

.bss   0x20000200  0x800
```

含义：

```text
.data = 512 字节 RAM
.bss  = 2048 字节 RAM

合计 = 2560 字节 RAM
```

Map 文件通常无法直接告诉你运行时某个任务的剩余栈空间、某次 malloc 分配的实际地址或实际最大栈深度。

#### 3.8.2 .su 文件
GCC 编译选项：

```text
-fstack-usage
```

可生成函数级别栈使用报告。

示意内容：

```text
process_data    4160    static
uart_send        128    static
```

表示编译器报告的函数栈用量和分析类别。

这里 `.su` 中的 `static` 指栈用量分析类别，和 C 语言的 `static` 变量不是一回事。

注意：

+ `.su` 主要报告单函数栈使用情况。
+ 不能只取最大单个函数数值就认定整个调用链的峰值。
+ 动态栈使用可能不能完整确定。
+ 仍需考虑函数嵌套和中断等额外开销。

#### 3.8.3 调试器
STM32CubeIDE 等调试器可以查看当前执行状态。

常见信息：

| 项目 | 作用 |
| --- | --- |
| PC | 程序计数器 |
| LR | 链接寄存器，保存返回相关信息 |
| MSP | 主栈指针 |
| PSP | 进程栈指针 |
| HFSR | HardFault 状态 |
| CFSR | 可配置故障状态 |
| BFAR | 部分总线故障的有效故障地址 |
| MMFAR | 部分存储器管理故障的有效地址 |


注意：故障状态寄存器的存在与内容因 Cortex-M 内核而异，BFAR、MMFAR 需要检查对应有效标志。

进入 HardFault 后，当前 PC 可能已指向 `HardFault_Handler()`，需要结合有效异常栈帧中的 PC 分析异常发生的位置。

#### 3.8.4 三者比较
| 需求 | 工具 |
| --- | --- |
| 查看 `.bss` 大小 | Map |
| 查看静态变量地址 | Map |
| 查看某函数编译期栈用量 | `.su` |
| 查看当前 MSP/PSP | 调试器 |
| 读取 HardFault 状态寄存器 | 调试器 |
| 估算历史最大栈深度 | 运行时高水位或其他监测机制 |


**记忆口诀：Map 看布局、SU 看函数栈、调试器看现场。**

### 3.9 栈溢出与堆栈碰撞
#### 3.9.1 栈溢出
假设：

```c
void process(void)
{
    uint8_t buffer[4096];

    uart_read(buffer, sizeof(buffer));
}
```

如果编译器在栈中安排该数组，且实际可安全使用的栈空间不足，就可能发生栈溢出。

可能表现为：

+ HardFault。
+ 随机死机。
+ 其他全局或动态数据被破坏。
+ 函数返回地址损坏。
+ 系统长时间运行后异常。

栈溢出不一定马上触发 HardFault。

#### 3.9.2 堆栈碰撞
在某些典型裸机单 RAM 区域实现中：

```text
高地址
    栈 ↓

    可用空间

    堆 ↑
    .bss
    .data
低地址
```

当堆和栈增长到相互重叠时，就可能发生堆栈碰撞。

这是栈溢出可能导致的一种内存破坏情形，但并非所有 STM32 工程都采用这种布局。

#### 3.9.3 为什么增大 Min_Stack_Size 不一定解决？
因为它通常只是链接阶段的最低预留设置。

真正需要判断：

1. 实际栈是否有足够空间？
2. 是否存在其他内存区域竞争？
3. 是否存在数组越界、非法指针等其他问题？
4. 是否有栈深度检测或硬件保护机制？

### 3.10 FreeRTOS 任务栈
#### 3.10.1 每个任务通常具有独立任务栈
在 FreeRTOS 中，每个任务一般具有独立的栈空间。

任务切换时，系统保存和恢复必要的执行上下文。

在典型 Cortex-M FreeRTOS 移植中：

+ MSP 常用于异常处理。
+ PSP 常用于任务执行。

这属于 ARM Cortex-M 的机制，不应直接套用到 ESP32-S3 Xtensa 架构。

#### 3.10.2 栈溢出检查
标准 FreeRTOS 支持相关检测配置，例如：

```c
#define configCHECK_FOR_STACK_OVERFLOW 2
```

可以结合溢出钩子函数进行调试。

具体生效方式依赖移植层和配置，不能保证捕获所有栈溢出。

#### 3.10.3 栈高水位
在启用了对应 API 的 FreeRTOS 环境中：

```c
UBaseType_t watermark =
    uxTaskGetStackHighWaterMark(NULL);
```

用于获取当前任务运行过程中测得的最小剩余栈空间。

注意单位：

+ 标准 Cortex-M FreeRTOS：通常按 `StackType_t` 单位。
+ ESP-IDF v5.5 ESP32-S3：相关任务栈大小和高水位接口按字节计算。

不能混淆不同移植版本的单位。

### 3.11 STM32 内存故障排查流程
假设程序新增 4096 字节局部数组后，偶尔发生 HardFault。

推荐按下面流程排查。

#### 3.11.1 步骤一：保存异常现场
利用调试器查看：

+ PC、LR。
+ MSP、PSP。
+ 适用内核的 HFSR、CFSR。
+ 有效的故障地址寄存器。
+ 调用栈和异常栈帧。

不能仅凭进入 HardFault 就断定栈溢出。

#### 3.11.2 步骤二：检查 Map
查看：

+ `.data`、`.bss` 占用。
+ RAM 区域和边界。
+ 链接脚本中的堆栈预留。
+ 是否存在大型静态数组。

#### 3.11.3 步骤三：检查 .su
查看：

+ 可疑函数栈使用。
+ 局部大数组。
+ 深层函数调用链。
+ 动态栈使用或递归。

#### 3.11.4 步骤四：检查运行时内存
确认：

+ 真实栈余量。
+ 是否存在堆栈碰撞风险。
+ malloc 是否分配失败。
+ 是否存在越界写入。
+ FreeRTOS 任务的栈高水位。

#### 3.11.5 步骤五：通过实验验证
可以在测试环境中：

+ 减少局部数组大小。
+ 改变缓冲区分配策略。
+ 增加适当的栈保护。
+ 检查访问边界。
+ 保留故障发生前后的日志。

**增加栈空间后故障消失，是线索，不是单独足以证明根因的证据。**

### 3.12 工程检查清单
实际编写 STM32/ESP32 驱动时：

1. 明确局部变量、静态变量和动态内存的生命周期。
2. 避免返回自动局部数组的地址。
3. 大型局部数组先评估栈用量。
4. malloc 成功后检查返回值，并明确释放责任。
5. 不把 static 误认为线程安全。
6. 使用 Map 查看静态 RAM 占用。
7. 使用 `.su` 辅助评估函数栈消耗。
8. 使用调试器检查运行现场。
9. 对 FreeRTOS 任务使用适当的栈高水位和溢出检测机制。
10. 遇到 HardFault 时先收集证据，再判断根因。

### 3.13 本章核心总结
**1. 存储期不等于内存区域。**

C 语言规定对象何时存在，编译器和链接器决定其具体布局。

**2. 普通局部对象通常使用栈，但不保证每个对象都入栈。**

寄存器分配、编译器优化会改变实际情况。

**3. static 局部对象具有静态存储期。**

它不会随着函数返回而消失，典型零初始化对象通常位于 `.bss`。

**4. malloc 分配的内存与局部指针是两个不同对象。**

指针消失不会自动释放堆内存。

**5. .data 和 .bss 的启动初始化机制不同。**

`.data` 通常从 Flash 复制初始内容，`.bss` 通常启动时清零。

**6. SP 负责管理当前栈，链接脚本负责静态布局。**

`_Min_Stack_Size` 不等于 CPU 强制的栈容量上限。

**7. Map、SU 和调试器承担不同职责。**

Map 看静态布局，SU 看函数栈使用报告，调试器看运行现场。

**8. HardFault 需要证据定位。**

不能只根据出现大数组、内存空间紧张等现象就认定栈溢出。

## 四、工程应用与常见陷阱

1. 堆栈大小不能只靠 `_Min_Stack_Size` 判断，必须结合实际可用 RAM、调用链、异常栈与运行时高水位。
2. 大局部数组改 static 会减少栈压力，但增加整个运行期 RAM 占用并可能破坏可重入性。
3. HardFault 先保存有效异常现场，不能仅凭看到大数组就认定栈溢出。

## 五、个人易错点与复盘

### 5.1 个人易错点记录
以下是本章学习过程中实际出现的错误，需要在后续复习中重点检查。

#### 5.1.1 易错点 1：static 局部数组误认为在栈上
错误理解：

```c
static uint8_t buffer[256];
```

因为声明在函数内部，所以在栈上。

正确理解：

它具有静态存储期，在典型 STM32 工程中零初始化时通常位于 `.bss`。

#### 5.1.2 易错点 2：指针自身与指向的内存混淆
```c
uint8_t *p = malloc(256);
```

正确区分：

```text
p：局部指针变量，通常在栈或寄存器
*p 所属动态分配内存：堆
```

指针变量不因为指向堆就自动存放在堆上。

#### 5.1.3 易错点 3：把内存泄漏叫内存溢出
漏掉 `free()`，且丢失全部有效引用，是内存泄漏。

这与访问越界或栈溢出不是同一个问题。

#### 5.1.4 易错点 4：十六进制地址计算错误
此前在 32 KB、64 KB RAM 地址计算中多次出现进位、减法错误。

重点记忆：

```text
16 KB = 0x4000
32 KB = 0x8000
64 KB = 0x10000
```

计算步骤：

1. 把容量转换成十六进制字节数。
2. 计算 RAM 结束边界。
3. 计算 PUSH 或 SUB 的实际字节数量。
4. 从初始 SP 中减去这些字节。
5. 检查结果是否处于合理地址范围内。

#### 5.1.5 易错点 5：把 Min_Stack_Size 理解成固定栈大小
错误：

```text
_Min_Stack_Size = 0x400
意味着栈只能使用1024字节
```

正确：

典型 STM32CubeIDE 链接脚本中，它用于最低预留及链接检查，不是硬件栈访问上限。

#### 5.1.6 易错点 6：混淆 Map、SU 与 MSP
错误：

利用 MSP 查询某个函数完整栈用量。

正确：

+ Map：静态布局。
+ SU：函数编译期栈用量报告。
+ MSP：CPU 当前主栈指针。
+ 调试器：当前执行现场和异常寄存器。

#### 5.1.7 易错点 7：认为函数返回会清空 RAM
函数返回后自动局部对象生命周期结束，栈空间通常可复用，但不意味着内存数据立即清零。

同理，`free()` 也不保证清零动态内存。

#### 5.1.8 易错点 8：改 static 就一定解决栈溢出
改 static 可能减少函数栈占用，但增加静态 RAM 占用，也可能引入并发访问问题。

必须根据实际根因决定修改方案。

## 七、参考答案与解析（完成自检后再看）

**1.** a 通常 .data；b、c 通常 .bss；d 通常栈（编译器可能优化）。

**2.** _estack=0x20008000，减 8+48=0x38，SP=0x20007FC8。

**3.** 非零初始值需要固件映像保存；启动代码从 Flash 的 LMA 复制到 RAM 的 VMA。

**4.** Map：段/符号链接地址；.su：单函数编译期栈用量；调试器：当前 CPU/异常现场。

**5.** 不能。该值在典型链接脚本用于最低预留/检查，不是 CPU 的栈访问边界；越界也可能静默破坏数据。
