### 二、模块、头文件与源文件
#### 2.1 什么是模块
模块是围绕一项职责组织起来的一组类型、函数和状态。

嵌入式工程中的常见模块：

+ UART 接收缓冲区。
+ IMU 驱动。
+ 通信协议解析。
+ 参数存储。
+ 电机控制。
+ 故障记录。

例如，UART 接收模块负责维护接收状态、提供读取接口；上层业务通过接口获取数据。

模块边界清楚，才能单独修改、测试和复用。

#### 2.2 头文件和源文件分别负责什么
| 文件 | 常见内容 | 作用 |
| --- | --- | --- |
| `.h` | 类型定义、宏、公共函数声明、必要的 extern 声明 | 告诉使用者如何调用模块 |
| `.c` | 函数实现、内部辅助函数、内部状态 | 完成模块的具体工作 |


示例：

```c
/* uart_status.h */
#ifndef APP_UART_STATUS_H
#define APP_UART_STATUS_H

#include <stdint.h>

int uart_get_status(uint8_t port);

#endif
```

```c
/* uart_status.c */
#include "uart_status.h"

int uart_get_status(uint8_t port)
{
    return port == 1u ? 1 : 0;
}
```

```c
/* main.c */
#include "uart_status.h"

int main(void)
{
    int status = uart_get_status(1u);
    return status == 1 ? 0 : 1;
}
```

执行关系：

1. `main.c` 包含头文件，获得函数声明。
2. 编译器据此检查调用处的参数和返回值使用。
3. `uart_status.c` 提供函数实现。
4. 链接器把调用与对应实现连接起来。

#### 2.3 声明与定义
声明说明名称及其类型等信息。

定义还提供函数体，或者构成对象定义。

```c
int get_count(void);          /* 函数声明 */

int get_count(void)           /* 函数定义 */
{
    return 3;
}

extern int device_count;     /* 对象声明，不是定义 */

int device_count = 0;        /* 对象定义 */
```

补充：

```c
int device_count;
```

在文件作用域下，这是一个暂定定义，不能简单当作普通的 `extern` 声明处理。

工程中共享全局对象通常采用：

```c
/* state.h */
extern int device_count;
```

```c
/* state.c */
#include "state.h"

int device_count = 0;
```

这样，公共声明放在头文件，实际对象由一个源文件提供。

#### 2.4 头文件保护解决什么问题
```c
#ifndef APP_UART_STATUS_H
#define APP_UART_STATUS_H

/* 头文件内容 */

#endif
```

它防止同一个头文件在同一翻译单元内重复展开。

它不负责：

+ 将 `.c` 文件加入工程。
+ 查找函数实现。
+ 自动链接同目录的 `.o`。
+ 消除不同源文件产生的多个外部定义。

因此，即使有头文件保护，也不应该随意在公共头文件中定义普通外部全局变量。

#### 2.5 为什么源文件要包含自己的头文件
假设头文件写：

```c
int uart_get_status(uint8_t port);
```

实现却写：

```c
int uart_get_status(uint16_t port)
{
    return port;
}
```

实现文件包含头文件后，编译器能够在同一个翻译单元中看到不兼容的声明和定义，并给出诊断。

如果实现文件没有包含公共头文件，普通的分文件编译和链接未必能发现跨文件类型不一致。

因此：

> 公共接口只维护一份正式声明，实现文件和使用文件都包含它。
>

### 三、编译、目标文件与链接
#### 3.1 什么是翻译单元
一个 `.c` 文件经过预处理，展开头文件和宏、处理条件编译后，形成翻译单元。

通常：

+ `main.c` 对应一个翻译单元。
+ `uart_status.c` 对应另一个翻译单元。
+ 两个源文件分别编译。

头文件提供的信息会分别进入包含它的翻译单元。

#### 3.2 编译和链接分别做什么
| 阶段 | 主要工作 | 常见问题 |
| --- | --- | --- |
| 预处理 | 展开头文件、宏和条件编译 | 找不到头文件、条件编译结果错误 |
| 编译 | 检查语法与类型并生成汇编等结果 | 类型冲突、语法错误 |
| 汇编 | 生成目标文件 | 汇编指令或目标配置问题 |
| 链接 | 组合输入，解析符号引用和安排地址 | 缺少定义、重复定义、区域溢出 |


日常说“编译工程”可能指整个构建过程；定位问题时要进一步区分具体阶段。

![](https://cdn.nlark.com/yuque/__mermaid_v3/c07484d2dad58df3e8bb5ff9ce151921.svg)

#### 3.3 目标文件中有什么
目标文件通常包含：

+ 机器代码。
+ 已初始化数据等节内容。
+ 符号信息。
+ 重定位信息。

例如，`main.o` 中可能包含：

+ `main` 的实现。
+ 对 `uart_get_status` 的未解析引用。

`uart_status.o` 中包含：

+ `uart_get_status` 的实现。

链接器根据本次输入中的符号信息，将这些部分组合起来。

目标文件通常还不是可以直接运行或烧录的完整程序。

#### 3.4 `-c` 的含义
```bash
gcc -std=c11 -Wall -Wextra -c main.c -o main.o
```

这条命令生成 `main.o`，不执行链接。

只要调用处具备正确声明，编译 `main.c` 时可以暂时没有函数实现的目标文件。

之后还需要：

```bash
gcc -std=c11 -Wall -Wextra -c uart_status.c -o uart_status.o

gcc main.o uart_status.o -o app
```

#### 3.5 目标文件存在，不代表已经参与链接
假设目录中已经存在：

+ `main.o`
+ `uart_status.o`

执行：

```bash
gcc main.o -o app
```

如果 `main.o` 调用了 `uart_get_status`，且本次链接的其他输入没有提供该定义，就会出现未定义引用等链接错误。

原因：

> 这条命令没有把 `uart_status.o` 作为链接输入，链接器不会因为它在同目录就自动使用它。
>

正确命令：

```bash
gcc main.o uart_status.o -o app
```

也可以让 GCC 一次完成编译和链接：

```bash
gcc -std=c11 -Wall -Wextra main.c uart_status.c -o app
```

#### 3.6 是否必须加入所有 `.o`
需要提供本程序所需的实现。

这些实现可以来自：

+ 直接列出的目标文件。
+ 指定的库。
+ 工具链或构建系统按配置加入的其他输入。

不应把目录中的全部 `.o` 无差别加入，原因包括：

+ 可能包含另一个测试程序的 `main`。
+ 可能包含同一模块的多个版本。
+ 可能产生重复定义。
+ 可能引入无关依赖。

#### 3.7 类型兼容与链接成功是两件事
```c
int get_value(void);
```

与：

```c
long get_value(void)
{
    return 1L;
}
```

返回类型不兼容。

即使某个平台上的 `int` 和 `long` 都是 4 字节，也不能据此认为它们是同一种类型。

同样：

```c
int read_port(uint8_t port);
```

不能随意实现为：

```c
int read_port(uint16_t port);
```

需要区分：

+ 调用实参可以按照语言规则发生类型转换。
+ 同一个函数的各处声明与定义必须满足类型兼容要求。

普通链接器通常围绕符号名解析实现，不能指望它完整替代 C 编译器的类型检查。

### 四、模块状态、多实例与结构体复制
#### 4.1 什么是模块状态
模块状态是执行过程中需要持续保存的信息，例如：

+ 当前读取位置。
+ 缓冲区地址。
+ 有效数据长度。
+ 已接收帧数。
+ 当前解析阶段。

如果函数内部只有一份隐藏的静态读取位置：

```c
static size_t cursor;
```

那么所有调用者都会访问同一个对象。

需要同时管理 UART1、UART2 时，这种设计可能让两个设备共用读取位置。

#### 4.2 使用上下文对象承载实例状态
```c
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

typedef struct {
    const uint8_t *data;
    size_t length;
    size_t cursor;
} RxReader;

bool rx_take(RxReader *reader, uint8_t *out)
{
    if (reader == NULL || out == NULL) {
        return false;
    }

    if (reader->data == NULL) {
        return false;
    }

    if (reader->cursor >= reader->length) {
        return false;
    }

    *out = reader->data[reader->cursor];
    ++reader->cursor;
    return true;
}

int main(void)
{
    const uint8_t uart1_data[] = {0x11u, 0x12u};
    const uint8_t uart2_data[] = {0x21u, 0x22u};

    RxReader uart1 = {
        .data = uart1_data,
        .length = sizeof uart1_data,
        .cursor = 0u
    };

    RxReader uart2 = {
        .data = uart2_data,
        .length = sizeof uart2_data,
        .cursor = 0u
    };

    uint8_t x = 0u;
    uint8_t y = 0u;

    bool ok1 = rx_take(&uart1, &x);
    bool ok2 = rx_take(&uart2, &y);

    return ok1 && ok2 && x == 0x11u && y == 0x21u ? 0 : 1;
}
```

执行结果：

| 对象 | 读取的数据 | 调用后 cursor |
| --- | ---: | ---: |
| uart1 | 0x11 | 1 |
| uart2 | 0x21 | 1 |


两个上下文对象占据不同的存储空间，因此各自维护自己的读取位置。

#### 4.3 复制结构体时，哪些内容被复制
```c
RxReader backup = uart2;
```

结构体成员的值被复制。

| 成员 | 复制后的关系 |
| --- | --- |
| `length` | 两份独立的整数成员，初始值相同 |
| `cursor` | 两份独立的整数成员，初始值相同 |
| `data` | 两份指针成员，保存相同地址 |


因此：

```c
backup.cursor = 0u;
```

不会同步修改 `uart2.cursor`。

但是：

```c
backup.data == uart2.data
```

成立，二者指向相同底层数据。

这里的 `data` 是指向只读数据的指针，不能通过它直接修改元素。

特别区分：

```c
struct A {
    uint8_t *data;
};

struct B {
    uint8_t data[8];
};
```

复制 `struct A` 时复制的是地址，不会复制地址所指向的整个缓冲区。

复制 `struct B` 时，结构体内部的数组元素也会随结构体一起复制。

#### 4.4 指针有效性和对象生命周期
上下文保存地址，不会延长所指对象的生命周期。

错误示例：

```c
RxReader make_reader(void)
{
    uint8_t local_data[] = {1u, 2u};

    RxReader reader = {
        .data = local_data,
        .length = sizeof local_data,
        .cursor = 0u
    };

    return reader;
}
```

函数返回后，局部数组生命周期结束，返回对象中的 `data` 不再指向有效的该数组对象。

工程中应明确：

+ 缓冲区由谁分配。
+ 缓冲区存活多久。
+ 谁可以修改。
+ 是否允许多个上下文共享。

#### 4.5 static 与多实例的关系
`static` 不等于“不能多实例”。

```c
static RxReader uart1_reader;
static RxReader uart2_reader;
```

仍然是两个不同对象。

问题出在是否把本应属于各实例的状态，设计成了所有调用者共用的一份对象。

另外，独立上下文不自动保证线程安全：

+ 多个任务访问同一个上下文，仍需同步。
+ ISR 与任务共享状态，仍需分析并发。
+ `volatile` 不能替代锁、临界区或原子操作。

### 五、接口契约、参数检查与错误返回
#### 5.1 什么是接口契约
接口契约是函数与调用者之间的明确约定。

至少说明：

| 项目 | 需要说明的问题 |
| --- | --- |
| 输入参数 | 是否允许 NULL，范围是多少 |
| 长度与容量 | 单位是字节、元素还是帧 |
| 内存 | 可读写范围、生命周期、是否允许重叠 |
| 返回值 | 每个状态代表什么 |
| 输出参数 | 哪些返回状态下有效 |
| 失败行为 | 是否保留原状态，是否可能部分写入 |
| 并发 | 是否允许多个任务或中断同时调用 |


函数有参数和返回值，并不意味着接口约定已经清楚。

#### 5.2 先检查，再解引用和修改
错误顺序：

```c
*out = reader->data[reader->cursor];

if (reader == NULL || out == NULL) {
    return false;
}
```

参数检查发生得太晚，前面的访问已经可能产生未定义行为。

合理顺序：

1. 检查必要指针。
2. 检查内部状态。
3. 检查是否还有数据。
4. 读取或写入。
5. 更新状态。
6. 返回成功。

#### 5.3 NULL 检查能检查什么
```c
if (out == NULL) {
    return false;
}
```

只能判断是否为空指针。

它不能证明：

+ 非空指针一定指向有效对象。
+ 指向的空间一定足够。
+ 对象仍在生命周期内。
+ 内存一定可写。

这些仍需接口契约、对象管理和调用者共同保证。

#### 5.4 空指针访问与内存泄漏的区别
| 问题 | 含义 |
| --- | --- |
| 空指针解引用 | 通过空指针访问对象，属于未定义行为 |
| 越界访问 | 访问对象允许范围之外的位置 |
| 悬空指针 | 指向生命周期已经结束的对象等无效目标 |
| 内存泄漏 | 动态分配的存储空间未被适当释放，持续占用资源 |


在 MCU 上，非法访问可能触发故障异常；具体表现取决于平台、地址映射和编译结果。

不能把所有内存问题统称为内存泄漏。

```c
++reader->cursor;
```

这里增加的是结构体的 `cursor` 整数成员。

如果 `reader` 无效，问题是访问无效对象；这条语句也不是在增加 `reader` 指针。

#### 5.5 状态码不能直接套用布尔含义
```c
typedef enum {
    RX_OK = 0,
    RX_BAD_ARG,
    RX_EMPTY,
    RX_BAD_STATE
} RxStatus;
```

这里成功值为 0。

错误判断：

```c
if (rx_read(&reader, &byte)) {
    /* 错把非零错误码当成成功 */
}
```

正确判断：

```c
RxStatus status = rx_read(&reader, &byte);

if (status == RX_OK) {
    /* 使用 byte */
}
```

判断规则由接口定义决定：

+ `bool` 接口可能用 `true` 表示成功。
+ 状态枚举可能用 0 表示成功。
+ 字节计数接口可能用负数表示错误。

#### 5.6 失败后，输出变量可能保留旧值
```c
uint8_t byte = 0x7Eu;
```

如果读取失败时函数没有写 `*out`，那么 `byte` 仍为 `0x7E`。

这不能证明本次读到了 `0x7E`。

必须同时检查返回状态。

同样，`0x00` 可以是正常接收的数据，不能单凭数据内容判断读取是否成功。

### 六、缓冲区容量、有效长度与字符串
#### 6.1 三种长度必须分清
```c
char text[3] = "OK";
```

| 项目 | 值 | 含义 |
| --- | ---: | --- |
| `sizeof text` | 3 | 数组对象占用的字节数 |
| `strlen(text)` | 2 | 首个零字符之前的字符数 |
| 当前存储内容 | `'O', 'K', '\0'` | 字符串连同终止符 |


`strlen` 不把结尾 `'\0'` 计入长度。

它要求输入已经是有效的、以零字符终止的字符串，不能拿它测量任意原始接收缓冲区。

#### 6.2 为什么文本长度必须小于容量
容量为 `capacity`，复制 `length` 个文本字节，再追加：

```c
dst[length] = '\0';
```

就要求：

```c
length < capacity
```

例如容量为 4：

| 文本长度 | 文本占用下标 | 终止符下标 | 是否能容纳 |
| ---: | --- | ---: | --- |
| 0 | 无 | 0 | 能 |
| 2 | 0、1 | 2 | 能 |
| 3 | 0、1、2 | 3 | 能 |
| 4 | 0、1、2、3 | 4 | 不能，终止符越界 |


检查通常写为：

```c
if (length >= capacity) {
    return TEXT_NO_SPACE;
}
```

#### 6.3 二进制数据和 C 字符串的区别
```c
uint8_t frame[] = {0xA5u, 0x00u, 0x12u, 0x34u};
```

这是 4 字节二进制数据。

其中的 `0x00` 是数据的一部分，不能使用 `strlen` 判断整帧长度。

| 类型 | 长度来源 |
| --- | --- |
| C 字符串 | 零字符终止，也可以额外保存长度 |
| 二进制帧 | 显式长度、协议字段或固定长度 |
| UART 接收缓冲区 | 驱动实际返回的接收字节数 |


如果把原始数据复制进 `char` 数组，但没有终止符，它仍不能直接作为有效字符串交给 `%s`。

#### 6.4 数组参数中的 sizeof 陷阱
```c
void process(uint8_t data[64])
{
    /* sizeof data 得到的是指针大小 */
}
```

函数形参中的这种数组写法会调整为指针类型。

推荐明确传递：

```c
void process(const uint8_t *data, size_t length);
```

需要写入时，还要根据接口设计传入容量：

```c
void fill(uint8_t *data, size_t capacity);
```

### 七、有符号返回值、类型转换与条件判断
#### 7.1 先理解返回值，再转换类型
接收接口可能约定：

| 返回值 | 含义 |
| ---: | --- |
| 小于 0 | 读取失败 |
| 等于 0 | 本次没有读到数据 |
| 大于 0 | 实际读到的字节数 |


如果返回结果是：

```c
int result = -1;
```

立即转换：

```c
size_t length = (size_t)result;
```

会把负数转换为一个很大的无符号值。

在 `size_t` 为 32 位的平台上，`-1` 转换后为：

```c
0xFFFFFFFF
```

在其他位宽的平台上，具体数值不同，不能把 `size_t` 永远当成 32 位。

#### 7.2 显式转换不会修复错误含义
```c
size_t a = result;
size_t b = (size_t)result;
```

对相同的负值，两者不会因为一个写了强制转换，就得到不同的正确业务结果。

显式转换可以表达转换意图，并可能抑制相应告警，但前提仍然需要正确。

推荐流程：

```c
if (result < 0) {
    puts("读取失败");
} else if (result == 0) {
    puts("没有可处理的数据");
} else {
    size_t length = (size_t)result;

    /* 按接口上限继续检查并处理 length */
    printf("收到 %zu 字节\n", length);
}
```

#### 7.3 比较与赋值
比较：

```c
result == 0
```

赋值：

```c
result = 0
```

错误代码：

```c
else if (result = 0)
```

先把 `result` 改成 0，再以赋值表达式的值判断条件，因此该条件为假。

这既改变了变量，又改变了分支行为。

#### 7.4 分支内声明变量使用花括号
本节使用 C11。

应写：

```c
else {
    size_t length = (size_t)result;
    printf("%zu\n", length);
}
```

花括号形成复合语句，也明确了变量作用域。

统一给分支和循环体加花括号，还能减少后续增加语句时的逻辑错误。

### 八、assert 的功能与执行原理
#### 8.1 assert 是什么
`assert` 是 `<assert.h>` 提供的宏。

它用于检查程序在某处应该满足的条件。

```c
#include <assert.h>

assert(cursor <= length);
```

含义是：

> 程序执行到这里时，开发者认为 cursor 不应该大于 length。
>

断言用于暴露程序逻辑或内部约束被破坏的问题。

#### 8.2 开启断言时会发生什么
以：

```c
assert(expression);
```

为例：

1. 程序执行到该位置。
2. 求值 `expression`。
3. 如果表达式非零，继续执行。
4. 如果表达式为零，报告断言失败并调用 `abort()`。

在嵌入式环境中，失败后的诊断、停止、异常或重启表现还受运行库和平台配置影响。

断言不是异常捕获，也不会自动恢复之前的变量状态。

#### 8.3 表达式中的函数会被调用
```c
assert(read_temperature() == 25);
```

开启断言时，必须先调用 `read_temperature()`，才能比较返回值。

即使最终断言失败，函数之前产生的副作用也已经发生，例如：

+ 增加读取次数。
+ 从 FIFO 取走数据。
+ 更新缓冲区位置。
+ 修改硬件状态。

断言失败不会撤销这些操作。

#### 8.4 NDEBUG 的关键是是否定义
常见命令行定义：

```bash
-DNDEBUG
```

下面这种定义同样会关闭标准 assert 检查：

```bash
-DNDEBUG=0
```

原因是检查 `NDEBUG` 是否被定义，而不是检查它的数值是否为 1。

在包含 `<assert.h>` 时定义了 `NDEBUG`，断言会成为不求值参数的空操作。

注意正确拼写：

```text
NDEBUG
```

#### 8.5 为什么不能把必要操作放进 assert
错误：

```c
assert(rx_accept(&ctx, data, count) == APP_OK);
```

开启断言时会调用 `rx_accept`。

关闭断言时，该调用不会执行。

这样，同一份业务代码会因为断言配置不同而改变行为。

正确组织：

```c
AppStatus status = rx_accept(&ctx, data, count);

if (status != APP_OK) {
    /* 根据业务处理失败 */
}
```

确实需要检查预期时，再额外写：

```c
assert(status == APP_OK);
```

必要调用已经发生，关闭断言不会将它删除。

#### 8.6 assert 和普通 if 如何分工
| 场景 | 通常采用的方式 |
| --- | --- |
| UART 超时、没有数据 | 正常返回状态并处理 |
| 传感器通信失败 | 检查驱动返回值 |
| 用户输入不合法 | 参数校验和错误返回 |
| 内部状态违反设计约束 | 断言辅助暴露问题 |
| 对外接口必须防止非法访问 | 保留正常运行时检查 |


不能因为调试版本中有断言，就删掉产品运行时必须依赖的边界检查。

### 九、完整工程案例：接收文本模块
#### 9.1 案例目标与接口约定
功能：

+ 接收驱动返回的有符号字节计数。
+ 区分无数据、读取错误和容量不足。
+ 成功后更新文本，并增加成功接收次数。
+ 失败时保留上下文原值。
+ 支持多个独立上下文。

本例采用内嵌数组：

```c
char text[8];
```

每个上下文都有自己的文本存储空间。

本例约定：

+ 单线程使用。
+ `ctx`、`src` 非空。
+ 正数计数对应至少这么多个可读源字节。
+ 源内容是文本片段，不包含零字节。
+ 源数据与目标上下文内存不重叠。
+ 成功计数统计调用成功的次数，不是字节总数。

接口不能仅凭一个指针和计数证明实际源空间足够，调用者必须满足约定。

#### 9.2 头文件：rx_app.h
```c
#ifndef APP_RX_APP_H
#define APP_RX_APP_H

#include <stddef.h>
#include <stdint.h>

enum {
    RX_TEXT_CAPACITY = 8
};

typedef enum {
    APP_OK = 0,
    APP_NO_DATA,
    APP_IO_ERROR,
    APP_NO_SPACE,
    APP_BAD_ARG
} AppStatus;

typedef struct {
    char text[RX_TEXT_CAPACITY];
    size_t accepted_frames;
} RxContext;

/*
 * 单线程接口。
 *
 * ctx、src 必须非空。
 *
 * read_result > 0 时：
 *   src 指向至少 read_result 个有效文本字节；
 *   文本不含零字节；
 *   src 所指源数据与 ctx 内存互不重叠。
 *
 * 成功：更新文本，成功次数加一。
 * 失败：保留 ctx 原值。
 */
AppStatus rx_accept(RxContext *ctx,
                    const uint8_t *src,
                    int read_result);

#endif
```

#### 9.3 实现文件：rx_app.c
```c
#include "rx_app.h"

#include <string.h>

AppStatus rx_accept(RxContext *ctx,
                    const uint8_t *src,
                    int read_result)
{
    if (ctx == NULL || src == NULL) {
        return APP_BAD_ARG;
    }

    if (read_result < 0) {
        return APP_IO_ERROR;
    }

    if (read_result == 0) {
        return APP_NO_DATA;
    }

    size_t length = (size_t)read_result;

    if (length >= sizeof ctx->text) {
        return APP_NO_SPACE;
    }

    memcpy(ctx->text, src, length);
    ctx->text[length] = '\0';

    ++ctx->accepted_frames;

    return APP_OK;
}
```

执行顺序：

![](https://cdn.nlark.com/yuque/__mermaid_v3/03b03c8fea108abd9158da5681f26f2d.svg)

实现中的关键安排：

1. 在解引用 `ctx` 之前检查指针。
2. 在转换为 `size_t` 之前处理负数。
3. 在复制之前检查文本容量。
4. 所有失败返回均发生在状态修改之前。
5. 成功路径才更新文本和计数。

#### 9.4 调用文件：main.c
```c
#include "rx_app.h"

#include <assert.h>
#include <stdio.h>

int main(void)
{
    const uint8_t ok[] = {
        'O', 'K'
    };

    const uint8_t ready[] = {
        'R', 'D', 'Y'
    };

    const uint8_t too_long[] = {
        '1', '2', '3', '4', '5', '6', '7', '8'
    };

    RxContext a = {
        .text = "OLD",
        .accepted_frames = 0u
    };

    RxContext b = {
        .text = "???",
        .accepted_frames = 0u
    };

    AppStatus first = rx_accept(&a, ok, 2);

    if (first != APP_OK) {
        return 1;
    }

    assert(a.accepted_frames == 1u);

    AppStatus error = rx_accept(&a, ok, -1);

    AppStatus full = rx_accept(&a, too_long, 8);

    AppStatus second = rx_accept(&b, ready, 3);

    if (second != APP_OK) {
        return 1;
    }

    printf("status: %d %d %d %d\n",
           (int)first,
           (int)error,
           (int)full,
           (int)second);

    printf("a=%s (%zu), b=%s (%zu)\n",
           a.text,
           a.accepted_frames,
           b.text,
           b.accepted_frames);

    return 0;
}
```

#### 9.5 执行过程
| 步骤 | 调用结果 | a.text | a.accepted_frames | b.text | b.accepted_frames |
| --- | --- | --- | ---: | --- | ---: |
| 初始化 | — | OLD | 0 | ??? | 0 |
| a 接收 2 字节 | APP_OK | OK | 1 | ??? | 0 |
| a 接收结果为 -1 | APP_IO_ERROR | OK | 1 | ??? | 0 |
| a 接收 8 字节 | APP_NO_SPACE | OK | 1 | ??? | 0 |
| b 接收 3 字节 | APP_OK | OK | 1 | RDY | 1 |


输出：

```text
status: 0 2 3 0
a=OK (1), b=RDY (1)
```

#### 9.6 构建方法
一次编译链接：

```bash
gcc -std=c11 -Wall -Wextra -Wconversion -Wsign-conversion -Werror -pedantic main.c rx_app.c -o app
```

分步编译链接：

```bash
gcc -std=c11 -Wall -Wextra -Wconversion -Wsign-conversion -Werror -pedantic -c main.c -o main.o

gcc -std=c11 -Wall -Wextra -Wconversion -Wsign-conversion -Werror -pedantic -c rx_app.c -o rx_app.o

gcc main.o rx_app.o -o app
```

关闭断言：

```bash
gcc -std=c11 -Wall -Wextra -Wconversion -Wsign-conversion -Werror -pedantic -DNDEBUG=0 main.c rx_app.c -o app_release
```

上述三种构建方式已在主机环境验证，业务输出一致。

原因是必要的 `rx_accept` 调用都放在断言外部。

#### 9.7 如果把容量判断改错
错误修改：

```c
if (length > sizeof ctx->text) {
    return APP_NO_SPACE;
}
```

当 `length == 8`：

1. 条件为假，没有拦截。
2. `memcpy` 向数组下标 0～7 复制 8 字节。
3. `ctx->text[8] = '\0'` 越界，产生未定义行为。

此时不能继续保证上下文状态、输出内容或程序运行结果。

即使越界前数组中已有 8 个字符，也不代表它是有效的 C 字符串。

### 十、STM32、ESP32-S3 与 FreeRTOS 中的应用
#### 10.1 STM32 多串口接收
可以为每个串口创建独立上下文：

```c
static RxContext uart1_context;
static RxContext uart2_context;
```

这样，每个串口拥有独立的：

+ 文本缓冲区。
+ 成功接收次数。
+ 后续可扩展的解析状态。

还要区分不同驱动接口：

+ STM32 HAL 的部分接收 API 返回 `HAL_StatusTypeDef`。
+ 返回状态不是实际接收字节数。
+ DMA 接收长度可能需要结合计数器或事件回调获取。

不能把不同平台的接收函数都按“负数错误、非负数字节数”解释。

在工程中新增源文件后，还要确认它实际参与构建，且没有被排除。

#### 10.2 ESP-IDF v5.5.4 UART 接收
`uart_read_bytes()` 返回有符号整数，按该 API 文档区分错误和实际读取字节数。

UART 驱动已经安装、参数和引脚已经配置之后，可以采用以下处理结构：

```c
#include <stdint.h>

#include "driver/uart.h"
#include "freertos/FreeRTOS.h"

void receive_once(void)
{
    uint8_t buffer[64];

    int result = uart_read_bytes(
        UART_NUM_1,
        buffer,
        sizeof buffer,
        pdMS_TO_TICKS(50)
    );

    if (result < 0) {
        /* 处理读取错误 */
        return;
    }

    if (result == 0) {
        /* 本次未读到数据 */
        return;
    }

    size_t length = (size_t)result;

    /*
     * 此时 buffer[0]～buffer[length - 1] 是有效数据。
     *
     * 按实际协议处理。
     * 不应默认 buffer 已经包含字符串终止符。
     */
    (void)length;
}
```

这是驱动初始化完成后的接收片段。

注意：

+ UART 是字节流。
+ 一次读取不一定得到一个完整协议帧。
+ 也可能读到多个帧或半个帧。
+ 缓冲、分帧和协议解析应分别明确职责。

本节的文本案例用于验证接口与边界，不能直接假设 UART 每次返回的内容都满足该文本接口约定。

#### 10.3 ESP-IDF 源文件怎样加入构建
组件的 `CMakeLists.txt` 可以明确列出源文件：

```cmake
idf_component_register(
    SRCS "app_main.c" "rx_app.c"
    INCLUDE_DIRS "."
)
```

含义：

+ `SRCS` 列出该组件的源文件。
+ `INCLUDE_DIRS` 指定头文件搜索目录。

配置头文件搜索路径，不会自动将对应 `.c` 实现加入编译。

ESP-IDF 应用使用：

```c
void app_main(void)
{
    /* 应用入口 */
}
```

前面的 `int main(void)` 是主机验证入口，移植时需要结合实际应用入口和驱动初始化组织代码。

#### 10.4 FreeRTOS 中的状态归属
建议先明确：

| 对象 | 示例 |
| --- | --- |
| 接收任务拥有的状态 | 当前接收缓冲区、分帧位置 |
| 解析任务拥有的状态 | 当前命令、校验结果 |
| 任务间传递的数据 | 队列元素、消息结构体或受控缓冲区 |


需要特别检查：

+ 队列复制的是完整数据，还是只复制指针。
+ 指针所指缓冲区会不会被接收任务覆盖。
+ 多任务是否同时修改同一个上下文。
+ 中断是否访问相同对象。

多实例设计解决状态组织问题；并发访问还需要独立设计同步机制。

### 十一、编译告警与代码规范
#### 11.1 常用告警选项
| 选项 | 主要用途 |
| --- | --- |
| `-Wall` | 开启一组常用告警 |
| `-Wextra` | 开启额外告警 |
| `-Wconversion` | 检查可能改变数值等隐式转换 |
| `-Wsign-conversion` | 检查可能改变符号含义的隐式转换 |
| `-Werror` | 将告警作为错误处理 |
| `-std=c11` | 选择 C11 语言模式 |


`-Wall` 并不表示开启所有告警。

无告警也不证明没有：

+ 越界。
+ 悬空指针。
+ 协议错误。
+ 并发竞争。
+ 错误的工程假设。

#### 11.2 遇到转换告警时怎么处理
按顺序检查：

1. 原值是否可能为负。
2. 目标类型能否表达全部合法值。
3. 转换之前是否完成范围检查。
4. 是否应该调整接口类型。
5. 最后再决定是否显式转换。

不应为了消除告警，直接给每处赋值加类型转换。

#### 11.3 命名与单位
变量名尽量说明含义：

```c
size_t received_bytes;
size_t accepted_frames;
size_t buffer_capacity;
size_t read_cursor;
```

区分：

+ 字节数。
+ 元素数。
+ 帧数。
+ 毫秒。
+ FreeRTOS tick。

例如，成功接收次数加一：

```c
++ctx->accepted_frames;
```

不能描述为“接收字节数加一”。

#### 11.4 本节建议采用的基本规范
1. 公共函数在头文件声明。
2. 实现文件包含自己的头文件。
3. 内部辅助函数使用文件作用域 `static`。
4. 分支和循环统一使用花括号。
5. 错误路径尽早返回。
6. 修改状态之前完成必要检查。
7. 比较状态码时使用明确的枚举名称。
8. 注释说明约定、原因和限制。
9. 对外暴露的接口明确长度单位、所有权与并发要求。
10. 根据实际构建输入排查编译链接问题。

### 十二、边界验证与工程排错
#### 12.1 文本接收模块的必要边界
容量为 8 字节时：

| 场景 | 预期结果 | 状态变化 |
| --- | --- | --- |
| `ctx == NULL` | APP_BAD_ARG | 不访问 ctx |
| `src == NULL` | APP_BAD_ARG | ctx 保持原值 |
| `read_result < 0` | APP_IO_ERROR | ctx 保持原值 |
| `read_result == 0` | APP_NO_DATA | ctx 保持原值 |
| 接收 1 字节 | APP_OK | 复制并追加终止符 |
| 接收 7 字节 | APP_OK | 终止符写在下标 7 |
| 接收 8 字节 | APP_NO_SPACE | ctx 保持原值 |


测试输入必须满足接口约定，例如正数长度对应足够的可读源空间。

#### 12.2 排错时先识别阶段
| 现象 | 优先检查 |
| --- | --- |
| 找不到头文件 | 包含路径和文件名 |
| conflicting types | 声明、定义和函数参数类型 |
| undefined reference | 对应实现是否进入本次链接 |
| multiple definition | 是否重复定义或重复加入实现 |
| 链接区域溢出 | 链接脚本、节大小和目标存储空间 |
| 程序运行后故障 | 指针、边界、栈、状态和并发 |


检查链接错误时：

1. 符号名称是否一致。
2. 实现是否被条件编译排除。
3. `.c` 是否进入本次构建。
4. 对应 `.o` 或库是否进入本次链接。
5. 对外函数是否误用了内部链接。
6. 是否拿错了构建目录或旧产物。

## 四、工程应用与常见陷阱

1. 字符串容量必须容纳结尾 '\0'，二进制字节数组则不一定需要终止符。
2. 接口接收有符号返回值时，先处理负数错误码，再转换为 size_t/无符号长度。
3. 对 ESP-IDF 项目检查 CMakeLists.txt 的 SRCS/PRIV_REQUIRES 等组件构建配置，而不是仅看源文件是否存在。

## 七、参考答案与解析（完成自检后再看）

**1.** 通常不能；若没有其他目标/库提供定义，会 undefined reference。

**2.** 让编译器在同一翻译单元校验外部函数签名、类型与接口一致，降低声明漂移风险。
