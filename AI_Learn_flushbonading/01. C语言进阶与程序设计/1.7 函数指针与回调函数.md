## 二、必须掌握的知识重点

| 核心知识 | 必须理解的规则与工程意义 |
|---|---|
| **声明与调用** | `int (*handler)(uint8_t)` 是指向函数的指针；`handler(v)` 会调用其当前保存的目标。 |
| **签名匹配** | 函数参数和返回类型必须兼容；不能通过不兼容函数指针强转调用来替代适配函数。 |
| **callback 与 ctx** | callback 是行为入口，ctx 是该行为要操作的对象；注册保存两者，分发按当前注册值调用。 |
| **生命周期** | 注册时传入的 ctx 指针指向的对象必须覆盖整个可能被回调访问的时期，不能保存即将失效的局部对象地址。 |
| **任务与 ISR** | 回调在哪个上下文被调用就遵守哪个上下文的 API/时延限制；队列存指针不等于保存帧副本。 |

## 三、系统知识讲解与代码分析

### 3.1 知识框架与用途
UART 驱动负责接收和组帧。应用层拿到完整帧后，可能解析协议、记录数据或更新状态。应用层可以把处理函数登记给驱动，驱动在数据就绪时调用登记的函数。这样，换处理逻辑时只需换注册参数。

| 概念 | 在驱动中的作用 |
| --- | --- |
| 函数指针 | 保存一个可调用的函数目标 |
| 回调 | 由应用层提供、由驱动在约定时机调用的函数 |
| 上下文 `ctx` | 回调要操作的设备状态或其他对象的地址 |
| 执行上下文 | 实际发起调用的是 ISR 还是任务，决定回调可用的接口 |

### 3.2 声明、赋值与调用
#### 3.2.1 从标识符向外读
```c
int (*handler)(uint8_t byte);
int *get_buffer(uint8_t channel);
```

`(*handler)` 表示 `handler` 是指针，右侧参数列表说明它指向一个接收 `uint8_t` 的函数，最左边的 `int` 是函数的返回类型。`get_buffer` 则是函数名，函数接收 `uint8_t`，返回 `int *`。

```c
typedef int (*ByteHandler)(uint8_t byte);

int decode(uint8_t byte);
ByteHandler handler = decode;
```

`ByteHandler` 是类型别名，`handler` 是能保存具体目标的变量。赋值时，`decode` 这个函数名转换为函数指针，也可写成 `&decode`。之后执行 `handler(0x12u)`，才通过保存的指针调用 `decode`。多个函数即使签名相同，也由赋值或注册操作选定当前目标。

#### 3.2.2 函数类型兼容性
参数类型、参数个数及返回类型要与接口约定兼容。`int decode_word(uint16_t)` 可以在直接调用时接收由 `uint8_t` 转换来的值，但它的函数类型与 `ByteHandler` 不兼容。

C 允许显式转换不同的函数指针类型，并保证转换回原类型后与原指针比较相等。通过转换后的不兼容类型调用该函数，行为未定义。要对接两个接口，在兼容的函数里转换参数值：

```c
#include <stdint.h>

typedef int (*ByteHandler)(uint8_t byte);

int decode_word(uint16_t word);

static int decode_byte_adapter(uint8_t byte)
{
    return decode_word((uint16_t)byte);
}

ByteHandler handler = decode_byte_adapter;
```

### 3.3 注册、分发和上下文
#### 3.3.1 从一次调用追到具体函数
注册函数把函数指针和对象地址保存到同一个处理器结构体。分发时，`handler` 决定从哪个结构体取配置，`callback` 决定调用哪个函数，`ctx` 决定把哪个对象交给回调。这三个值可以分别追踪。

下面是可独立运行的 C11 示例，用一条模拟 UART2 帧验证这条路径：

```c
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

typedef void (*FrameCallback)(const uint8_t *data, size_t len, void *ctx);

typedef struct {
    FrameCallback callback;
    void *ctx;
} RxHandler;

typedef struct {
    uint8_t last_frame_type;
    unsigned int frame_count;
} PortState;

static void register_rx_callback(RxHandler *handler,
                                 FrameCallback callback, void *ctx)
{
    handler->callback = callback;
    handler->ctx = ctx;
}

static void dispatch_frame(const RxHandler *handler,
                           const uint8_t *data, size_t len)
{
    if (handler->callback != NULL) {
        handler->callback(data, len, handler->ctx);
    }
}

static void on_frame(const uint8_t *data, size_t len, void *ctx)
{
    PortState *state = ctx;

    if (len == 3u) {
        state->last_frame_type = data[0];
        state->frame_count++;
    }
}

int main(void)
{
    static RxHandler uart1_handler, uart2_handler;
    static PortState uart1_state, uart2_state;
    const uint8_t received[] = {0x07, 0x03, 0x02};

    register_rx_callback(&uart1_handler, on_frame, &uart1_state);
    register_rx_callback(&uart2_handler, on_frame, &uart2_state);
    dispatch_frame(&uart2_handler, received, sizeof received);

    printf("UART1: type=%u count=%u\n",
           (unsigned)uart1_state.last_frame_type, uart1_state.frame_count);
    printf("UART2: type=%u count=%u\n",
           (unsigned)uart2_state.last_frame_type, uart2_state.frame_count);
    return 0;
}
```

两次注册都只保存配置。唯一一次分发读取的是 `uart2_handler`，因此调用效果等价于 `on_frame(received, 3u, &uart2_state)`。输出是 UART1 的类型、计数为 `0、0`，UART2 为 `7、1`。两个 UART 共用函数代码，各自拥有状态对象。

#### 3.3.2 ctx 的类型和寿命
驱动用 `void *` 保存对象地址，回调按约定转回 `PortState *` 后再访问。回调应使用与注册时实际对象匹配的类型。结构体对象用 `uart2_state.frame_count`，通过结构体指针访问则写 `state->frame_count`。

```c
void app_init(void)
{
    PortState state = {0};
    register_rx_callback(&uart2_handler, on_frame, &state);
}
```

如果 `uart2_handler` 在 `app_init()` 返回后仍保留注册配置，以上写法有悬垂指针问题。`state` 是自动对象，函数返回时生命周期结束。长期注册可使用静态状态，或由调用方提供寿命覆盖注册期间的设备实例。撤销注册前还要考虑已经开始或等待执行的回调。运行中更换回调时，应同步更新 `callback` 和 `ctx`，避免分发方读到一新一旧的配置。

### 3.4 工程应用：UART ISR 收帧，任务调用回调
#### 3.4.1 调用顺序
以固定 3 字节的演示协议为例。初始化阶段创建队列、注册处理器，然后启用接收。接收任务可以先在 `xQueueReceive()` 等待。

| 阶段 | 运行位置 | 操作 |
| --- | --- | --- |
| 收到字节 | UART ISR | 写入组帧缓冲区，更新已接收长度 |
| 一帧收齐 | UART ISR | 把帧复制进队列，随后原接收缓冲区可用于下一帧 |
| 任务被调度 | 接收任务 | `xQueueReceive()` 返回，任务取得自己的帧副本 |
| 应用处理 | 接收任务 | 调用 `dispatch_frame()`，间接调用登记的回调 |


回调在发起调用的上下文中同步执行。如果 ISR 直接调用分发函数，回调也处于 ISR 上下文，需要遵守该端口的中断优先级和 ISR API 约束。由任务分发时，回调可以按任务上下文的约束处理数据。

#### 3.4.2 短帧队列按值传递
```c
#include <stdint.h>
#include "FreeRTOS.h"
#include "queue.h"

typedef struct {
    uint8_t bytes[3];
} RxFrame;

/* 前提：队列项大小为 sizeof(RxFrame)，data 指向完整的 3 字节帧。
 * ISR 调用者先将 *task_woken 初始化为 pdFALSE。
 */
BaseType_t post_frame_from_isr(QueueHandle_t queue,
                              const uint8_t *data,
                              BaseType_t *task_woken)
{
    RxFrame frame = { .bytes = {data[0], data[1], data[2]} };
    return xQueueSendFromISR(queue, &frame, task_woken);
}
```

发送成功后，队列保存的是三个字节的副本，函数返回后局部 `frame` 可以结束生命周期。队列满时发送失败，调用方应按工程要求记录丢帧或处理过载。如果 `*task_woken` 为 `pdTRUE`，调用方按所用移植层的约定请求退出 ISR 后切换任务。

任务取到 `RxFrame received` 后，可调用 `dispatch_frame(&uart2_handler, received.bytes, sizeof received.bytes)`。若两路 UART 共用队列，可在队列项里加端口编号。

如果队列项换成指针类型，队列只复制地址。即便原缓冲区一直有效，下一帧也可能覆盖上一帧。长帧若采用零拷贝，需要明确缓冲区所有权，并等消费者归还后再重用。回调收到的 `const uint8_t *data` 只限制通过该指针写入，缓冲区能用多久仍取决于接口约定。


### 3.5 回调的执行语义与多实例

### 3.6 回调不是独立线程，也不是自动异步
```c
typedef void (*EventCb)(void *ctx, int event);
typedef struct {
    EventCb cb;
    void *ctx;
} Handler;

void dispatch(Handler *h, int event)
{
    if (h != NULL && h->cb != NULL) {
        h->cb(h->ctx, event);
    }
}
```
这次调用通常与直接调用普通函数一样同步完成。所谓“回调”描述谁决定调用时机，不等同于函数自动运行在新线程中；回调真正运行在触发 `dispatch` 的线程或 ISR 上下文。

### 3.7 注册时应一起保存函数和状态
```text
UART1 handler ── cb ───┐
                 ctx ──┼──► UART1_state
UART2 handler ── cb ───┤
                 ctx ──└──► UART2_state
```
两个实例可以复用一份 `cb` 代码，但是 `ctx` 应分别指向自己的状态。单次分发只有所选的 handler 会执行；重复注册一般覆盖原目标，不会自动建立多个订阅者。


## 四、工程应用与常见陷阱

1. 多个 UART 可复用同一回调函数，但每个端口应持有各自的状态 ctx，避免全局状态串扰。
2. ISR 内回调不能执行可能阻塞的普通队列/互斥锁 API；必要时在 ISR 中入队、让任务完成协议处理。
3. 运行时同时更新 callback 与 ctx 需要同步，避免读到旧函数搭配新上下文；撤销回调前考虑尚未执行的事件。

### 5.1 本节易错回顾
| 易错点 | 怎样检查 |
| --- | --- |
| 以为同签名的函数会被自动选中 | 找到传入注册函数的实参，再看它存到哪个 `handler` |
| 以为回调负责初始化接收缓冲区 | 跟踪缓冲区写入、组帧完成和回调触发三个时刻 |
| 看到 UART2 分发就认定一定修改 UART2 状态 | 同时检查实际传给回调的 `ctx` |
| 只看 `ctx` 保存在哪儿 | 确认它所指的对象到回调执行时仍有效 |
| 强转后就调用不同签名的函数 | 用签名兼容的适配函数，在函数体内转换参数值 |
| 队列存指针，以为保存了整帧 | 检查队列项类型、缓冲区寿命和重用时机 |

## 七、参考答案与解析（完成自检后再看）

**1.** 前者是函数指针；后者是一个函数，它接收 uint8_t，返回 int*。

**2.** 不安全；不兼容类型的函数指针调用可能触发未定义行为；应写参数/返回类型匹配的 adapter。

**3.** 通常执行最新保存的 count_frame，假设注册 API 是覆盖式且未设计多订阅。

**4.** ctx 悬空；需使用寿命足够长的对象并定义撤销注册与同步机制。

**5.** 队列项若是指针只复制地址，接收缓冲区可能在任务读取前被下一帧覆盖。
