## 三、系统知识讲解与代码分析

### 一、本节解决什么问题
+ **宏**在预处理时生成代码或常量。分析宏时，先写出展开结果，再看优先级和实际求值次数。
+ **条件编译**决定哪些代码进入本次构建。例如调试版编译 GPIO 跟踪，发布版省略跟踪。
+ **位运算**在 C 表达式里构造、提取和修改位。表达式的类型决定运算宽度，赋值转换决定最终保存的值。
+ **寄存器访问**把一个值写到指定地址。硬件根据该地址和字段定义解释写入，因此同一个 1 可能表示设置输出、发出复位命令，或者清除挂起标志。

### 二、宏的工作方式
#### 2.1 对象式宏、函数式宏与编译阶段
对象式宏由名称直接触发替换，例如 `#define UART_RX_CAPACITY 128u`。函数式宏在使用处跟着参数列表时展开，例如 `PIN_MASK(5u)`。预处理器处理的是记号，类型检查和实际表达式求值由后续 C 编译阶段负责。宏本身没有对象类型和可取地址的存储。展开出来的表达式可以有类型，也可以产生实际的运行时代码。

```c
#define UART_RX_CAPACITY 128u
#define PIN_MASK(n)     (1u << (n))
```

`UART_RX_CAPACITY` 可以直接用于 `#if`。相比之下，`static const unsigned rx_capacity = 128u;` 是 C 对象，可以由 C 代码访问，预处理器无法查询它的值。两者应按用途选择。

#### 2.2 参数括号与整体括号分别保护什么
| 写法 | 调用 | 展开后按优先级理解 | 结果 |
| --- | --- | --- | ---: |
| `#define BAD_MASK(n) 1u << (n)` | `BAD_MASK(5u) + 3u` | `1u << (5u + 3u)` | `0x100` |
| `#define PIN_MASK(n) (1u << (n))` | `PIN_MASK(5u) + 3u` | `(1u << 5u) + 3u` | `0x23` |
| `#define BAD_MASK(n) (1u << n)` | `BAD_MASK(1u | 2u)` | `(1u << 1u) | 2u` | `0x02` |
| `#define PIN_MASK(n) (1u << (n))` | `PIN_MASK(1u | 2u)` | `1u << (1u | 2u)` | `0x08` |


在第一行，`+` 的优先级高于 `<<`，所以外部的 `+ 3u` 进入了移位量。第三行里，`<<` 的优先级高于 `|`，所以少了参数括号后，实参里的 `| 2u` 跑到了移位表达式外。对于返回表达式的宏，给每个形参加括号，并给整个替换表达式加括号。

括号解决结合方式。调用者还要保证移位量合法。例如这里左侧是 32 位的 `1u`，移位量范围为 0～31。

#### 2.3 参数重复求值与 FIFO 副作用
```c
#define MAX(a, b) (((a) > (b)) ? (a) : (b))

uint8_t sample = MAX(uart_fifo_pop(), 100u);
```

展开后，`uart_fifo_pop()` 同时出现在比较表达式和条件成立分支。假设 FIFO 前两字节是 140、129。

1. 执行比较时，第一次出队取走 140。
2. `140 > 100` 成立，进入 `?` 后面的分支。
3. 执行这个分支时，第二次出队取走 129，最终 `sample = 129`。
4. 如果第一次读到的字节小于或等于 100，就进入返回 100 的分支，本次调用只出队一次。

函数调用、`i++`、某些外设寄存器读取都可能改变状态。对这类实参，先做一次动作并保存结果。可以用有类型的 `static inline` 函数实现比较。

```c
#include <stdint.h>

static inline uint8_t max_u8(uint8_t a, uint8_t b)
{
    return a > b ? a : b;
}

// 调用示例，假设 FIFO 已确认非空
uint8_t first = uart_fifo_pop();
uint8_t sample = max_u8(first, 100u);
```

这段代码只取走 140，比较结果也为 140。函数的每个实参会求值一次。若多个实参都有副作用，仍要避免依赖 C 未指定的实参求值顺序。`inline` 也不保证编译器一定把函数体展开。

#### 2.4 多语句宏与语句边界
假设一个跟踪宏需要先拉高 GPIO，再记录标记。把两个语句直接放在宏替换体里，宏展开到无花括号的 `if/else` 时，可能有一条语句跑出 `if`，或者导致 `else` 无法配对。用 `do { ... } while (0)` 包成一条语句，调用处正常写分号。

```c
#define TRACE_MARK(tag)           \
    do {                          \
        trace_pin_high();         \
        trace_emit((tag));        \
    } while (0)

if (frame_ready)
    TRACE_MARK(frame_type);
else
    handle_idle();
```

多行宏用反斜杠续行。宏定义的 `while (0)` 后不写分号，由调用处补齐。语句宏内部若使用 `break`，会跳出宏自己的 `do/while`，因此这类宏应尽量保持控制流简单。

#### 2.5 字符串化、记号拼接和可变参数
```c
#define STR_RAW(x) #x
#define STR(x)     STR_RAW(x)
#define JOIN_RAW(a, b) a ## b
#define JOIN(a, b)     JOIN_RAW(a, b)
#define PORT_NO 2

STR_RAW(PORT_NO)      // "PORT_NO"
STR(PORT_NO)          // "2"
JOIN(uart, PORT_NO)   // uart2
```

`#` 把参数变成字符串字面量。`##` 拼出一个合法的预处理记号。实参直接用于这两种操作时，该位置不会先做通常的宏展开。外层宏把实参展开后再传到内层，因此可以得到 `"2"` 或 `uart2`。

C11 支持使用 `...` 和 `__VA_ARGS__` 转发一组参数。把格式串包含在可变参数里，可以让有格式参数和只有格式串的调用都用同一个定义。

```c
#define TRACE_LOG(...) do { trace_printf(__VA_ARGS__); } while (0)

TRACE_LOG("ready");
TRACE_LOG("rx=%u", (unsigned)rx_count);
```

#### 2.6 查看编译器实际拿到的代码
以 GCC 为例，`-E` 只运行预处理，`-P` 去掉行号标记。检查真实工程时，保留原构建命令中的目标、头文件搜索路径和 `-D` 参数。

```bash
gcc -std=c11 -E -P -DTRACE_GPIO_ENABLE=0 trace_demo.c
gcc -std=c11 -E -P -DTRACE_GPIO_ENABLE=1 trace_demo.c
```

比较两次输出，可以确认宏如何展开，以及哪些函数定义和调用仍会进入编译阶段。

### 三、条件编译与构建开关
#### 3.1 按“是否定义”还是按“数值”选择
| `TRACE_GPIO_ENABLE` 的输入状态 | `#ifdef `<br/>`TRACE_GPIO_ENABLE` | `#if `<br/>`TRACE_GPIO_ENABLE` | `#if defined(TRACE_GPIO_ENABLE) && TRACE_GPIO_ENABLE` |
| --- | --- | --- | --- |
| 未定义 | 跳过 | 跳过，未定义标识符按 0 处理 | 跳过 |
| 定义为 0 | 进入 | 跳过 | 跳过 |
| 定义为 1 | 进入 | 进入 | 进入 |


表格按数值型定义讨论。空替换列表的宏适用于存在性检查，直接用于数值表达式可能造成预处理语法错误。GCC 的 `-Wundef` 可以帮助发现数值条件里的未定义标识符。

```c
#ifndef TRACE_GPIO_ENABLE
#define TRACE_GPIO_ENABLE 0
#endif

#if TRACE_GPIO_ENABLE
void trace_emit(uint32_t tag);
#define TRACE_TAG(tag) do { trace_emit((tag)); } while (0)
#else
#define TRACE_TAG(tag) do { } while (0)
#endif
```

这里 `#ifndef` 只在构建系统没有传值时提供默认值，`#if` 决定是否编入跟踪代码。`#elif` 可以继续选择其他配置，`#else` 是兜底，`#endif` 结束本组条件。头文件的 include guard 则适合使用 `#ifndef` 判断该头文件是否已经展开过。

普通 C 的 `if` 由编译器处理，分支中的 C 代码需要通过语法与语义检查，常量条件有可能在后续优化中被折叠。预处理的 `#if` 在这之前筛选代码，适合控制芯片专用头文件、可选驱动和构建配置。

#### 3.2 用于 STM32 构建和 ESP-IDF 项目配置
STM32 项目可以让 Debug 构建定义 `TRACE_GPIO_ENABLE=1`，Release 定义 `TRACE_GPIO_ENABLE=0`。GPIO 跟踪专用的初始化、定义和调用应有一致的开关。功能代码应先完成必要的数据读取，再将已取得的值送给日志。上述关闭版本不会求值 `TRACE_TAG` 的实参，把 `uart_fifo_pop()` 放进去会让接收行为随构建配置变化。

ESP-IDF v5.5.4 项目可在组件 `Kconfig` 中声明自定义布尔选项，由 `menuconfig` 配置。在 C 源码包含 `sdkconfig.h` 后，可以通过 `#if defined(CONFIG_APP_UART_TRACE)` 选择是否编入该布尔选项对应的跟踪代码。这里的 `APP_UART_TRACE` 是项目自定义名称。

### 四、位运算与类型推导
#### 4.1 单个位、掩码和常见判断
以下例子用 `uint32_t` 保存 32 位值。bit 0 是最低位，`UINT32_C(1) << n` 生成仅 bit n 为 1 的掩码。例 `UINT32_C(1) << 5u` 得到 `0x00000020`。

| 目的 | 表达式 | 当掩码某位为 1 |
| --- | --- | --- |
| 保留被选中的位 | `value & mask` | 该结果位等于原值 |
| 置位 | `value | mask` | 该结果位置 1 |
| 清位 | `value & ~mask` | 该结果位清 0 |
| 翻转 | `value ^ mask` | 该结果位取反 |
| 测试是否至少有一个目标位为 1 | `(value & mask) != 0u` | 任意一位命中即可 |
| 测试目标位是否全部为 1 | `(value & mask) == mask` | 所有目标位都须命中 |


例 `value = 0x29`，`mask = 0x28`。保留目标位得到 `0x28`，清目标位得到 `0x01`。写位判断时要保留括号。把 `(value & mask) == mask` 写成 `value & mask == mask`，会先计算 `mask == mask`，再与 `value` 做按位与。

`&` 和 `|` 逐位计算，两侧表达式都会求值。`&&` 和 `||` 做真假判断，结果是 0 或 1，并可能跳过右侧表达式。

#### 4.2 小整数为什么按 int 运算
```c
uint8_t sample = 129u;        // 0x81
int shifted = sample << 2u;   // 516 = 0x204
uint8_t packed = (uint8_t)shifted;  // 4 = 0x04
```

移位会分别对两个操作数做整数提升。左侧 `uint8_t` 的 0～255 都能由 `int` 表示，所以提升为 `int`。右侧 `2u` 是 `unsigned int`，移位表达式的结果类型由**提升后的左操作数**决定，仍为 `int`。计算完得到 `129 × 4 = 516`，随后转换到 `uint8_t` 时取模 256，得到 4。把强制转换去掉，赋值仍会发生同样的转换。

同理，`~` 也会先做整数提升。在本节的 32 位平台上，若 `uint8_t m = 0x0Fu;`，`~m` 先在 `int` 宽度上运算。需要一个 8 位取反结果时，用 `uint8_t inverted = (uint8_t)~m;`，得到 `0xF0`。需要寄存器的 32 位反掩码时，先把掩码明确为 `uint32_t` 再取反。

#### 4.3 移位边界与高位构造
+ 移位量为负，或达到提升后左操作数的位宽时，行为未定义。32 位操作数允许 0～31。
+ C11 中，带符号左操作数为负，或非负值左移后无法用该有符号结果类型表示时，行为未定义。按 32 位 `int` 举例，`1 << 31` 就触发了这个边界。
+ `UINT32_C(1) << 31u` 在本节平台上得到 `0x80000000`。构造高位时，从一开始就使用无符号类型。先做错误移位，再把结果转成 `uint32_t`，已经太晚。
+ 无符号右移在高位补 0。C11 对负数的有符号右移由实现定义，寄存器和协议字段提取应使用无符号值。

#### 4.4 多位字段的读、清和填
假设某个 32 位寄存器的字段在 bit 11:10，宽度为 2，起始位为 10。可表示的字段值为 0～3。

```c
const uint32_t shift = 10u;
const uint32_t field_mask = UINT32_C(0x3) << shift;  // 0x00000C00

uint32_t field = (old_value & field_mask) >> shift;
uint32_t new_value = (old_value & ~field_mask)
                   | ((requested_mode << shift) & field_mask);
```

这里 `old_value` 和 `requested_mode` 都是 `uint32_t`。读取时保留 bit 11:10，再移到低位。替换时先把旧字段两位清掉，再把新字段移到正确位置。末尾的掩码限制新值影响的范围，调用者仍需检查 `requested_mode <= 3u`，以免静默截去高位。

以 STM32F407 的 `GPIOA->MODER` 为例，PA5 模式就在 bit 11:10。假设 GPIOA 已启用时钟，初始化代码独占配置，旧字段为 `10`，目标是通用输出模式 `01`。直接 OR 会变成 `11`。正确计算是先清 `0x00000C00`，再填 `0x00000400`。

```c
uint32_t mode = GPIOA->MODER;
mode &= ~UINT32_C(0x00000C00);
mode |=  UINT32_C(0x00000400);
GPIOA->MODER = mode;
```

STM32F103 的 GPIO 配置使用 `CRL/CRH`，上面的 `MODER` 代码属于 STM32F407。

### 五、STM32F103 的 GPIO 寄存器定义与访问宽度
#### 5.1 分开看 C 成员宽度、硬件有效位和允许的访问宽度
在 STM32F103 的 ST CMSIS 设备头文件中，`GPIO_TypeDef` 的 `IDR`、`ODR`、`BSRR` 成员都是 `__IO uint32_t`。在这个目标上，`uint32_t` 是 32 位，占 **4 个字节**。`__IO` 带有 `volatile` 限定，硬件的只读、只写等访问权限仍以参考手册为准。

STM32F103 的 GPIOA 基地址是 `0x40010800`。寄存器表中的 offset 按字节计算。

| 寄存器 | 相对偏移 | GPIOA 地址 | C 成员宽度 | 有效字段和含义 | RM0008 访问方式 |
| --- | ---: | ---: | ---: | --- | --- |
| `IDR` | `0x08` | `0x40010808` | 4 字节 | bit 15:0 是输入采样，bit 31:16 保留 | 32 位字读，只读 |
| `ODR` | `0x0C` | `0x4001080C` | 4 字节 | bit 15:0 是输出锁存数据，bit 31:16 保留 | 32 位字访问，可读可写 |
| `BSRR` | `0x10` | `0x40010810` | 4 字节 | bit 15:0 是置位命令，bit 31:16 是复位命令 | 32 位字写，只写 |


**两个 16 位半区属于同一个 32 位 BSRR。** `ODR` 有 16 个有效数据位，仍按 4 字节访问。对于本系列，按手册使用 32 位字访问这三个 GPIO 寄存器。换型号时重新查寄存器布局、允许的访问宽度和头文件字段。

在 STM32F103 工程中，可以直接用设备头文件做编译期检查。下面的 `sizeof` 不读取外设，`offsetof` 给出结构体成员相对起点的字节偏移。

```c
#include <stddef.h>
#include "stm32f103xb.h"

_Static_assert(sizeof(GPIOA->ODR) == 4, "ODR width");
_Static_assert(sizeof(GPIOA->BSRR) == 4, "BSRR width");
_Static_assert(offsetof(GPIO_TypeDef, ODR) == 0x0C, "ODR offset");
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x10, "BSRR offset");
```

这个检查回答的是 **C 定义宽度与布局**。判断哪些位有效、软件写进去有什么效果，还要看 RM0008 对该字段的说明。

#### 5.2 ODR 是输出锁存值，IDR 是引脚采样值
`GPIOA->ODR` 的 bit 7 对应 PA7 的输出锁存值。读取它可以确认软件设置的输出数据。读 `GPIOA->IDR` 的 bit 7 则用于看输入采样所见的引脚电平。例子中假设 GPIOA 已开启时钟，目标引脚配置成普通推挽输出，输出锁存值才直接对应这里讨论的拉高、拉低。开漏配置下，写 1 会释放输出，实际高电平由外部上拉等电路条件决定。

如果写 `GPIOA->ODR = 1u << 7u;`，这次写入会把其他有效 ODR 位写成 0。若只想改变 PA7，可用 `BSRR` 发送单独的置位命令。

#### 5.3 BSRR 每一位的映射
对引脚编号 `n`，范围为 0～15。

| 目标 | 往 BSRR 哪一位写 1 | 该位置写 0 时 |
| --- | --- | --- |
| 将 ODR 的 bit n 置 1 | bit n，低半区的 `BSn` | 无动作 |
| 将 ODR 的 bit n 清 0 | bit n + 16，高半区的 `BRn` | 无动作 |


以 PA4 为例，bit 4 写 1 对应置位，bit 20 写 1 对应复位。因此，**要把 PA4 清 0，写入数据里的 bit 20 必须是 1**。如同一条写入同时对同一引脚提出置位和复位请求，RM0008 规定置位优先。写业务代码时应让两组掩码分开，便于检查每个引脚的意图。

RM0008 把 BSRR 字段标为 `w`，其寄存器记法约定读取只写位会返回复位值。要核实输出状态读 `ODR`。写 `BSRR` 时直接赋值，`|=` 会额外发起一次读取。

#### 5.4 完整推导一次写入
目标是初始 `ODR = 0x0029` 时，拉低 PA3、PA5，拉高 PA6、PA9，保留其他引脚状态。

| 动作 | 对应 ODR 位 | 实际要写入的 BSRR 位 | 掩码 |
| --- | --- | --- | ---: |
| 拉低 PA3 | 3 | 19 | `0x00080000` |
| 拉低 PA5 | 5 | 21 | `0x00200000` |
| 拉高 PA6 | 6 | 6 | `0x00000040` |
| 拉高 PA9 | 9 | 9 | `0x00000200` |


```c
const uint32_t reset_mask = (1u << 3u) | (1u << 5u);  // 0x0028
const uint32_t set_mask = (1u << 6u) | (1u << 9u);    // 0x0240

GPIOA->BSRR = (reset_mask << 16u) | set_mask;         // 写 0x00280240
```

按硬件动作推导 `ODR` 的结果，在本例可写成 `(0x0029 & ~0x0028) | 0x0240`，结果是 `0x0241`。这是**分析硬件时的等式**。实际代码通过 BSRR 一次写入，不需要先读取 ODR。低位的 PA0 起初为 1，两组命令都没选它，所以保持 1。

#### 5.5 为什么 BSRR 能避开一次读改写
对普通 RW 寄存器，`GPIOA->ODR |= 1u << 7u;` 的逻辑步骤为读旧 ODR、在 CPU 中 OR、再写整个 ODR。假设主循环读到 `0x0001`，ISR 随后把 PA2 置 1，ODR 变成 `0x0005`。主循环按旧值算出的 `0x0081` 写回时，PA2 的更新就丢了。

BSRR 的单次写入只给目标位发命令。若两处都通过 BSRR 修改不同引脚，各自的命令不会覆盖对方所改的位。若仍有代码整字写 ODR，或两处竞争同一引脚，则需要约定谁负责写。寄存器成员的 `volatile` 限定无法让一组读、算、写变成不可分割的操作。

### 六、STM32F103 的 EXTI_PR 与写 1 清零
#### 6.1 先读懂访问属性
`EXTI->PR` 是 EXTI 的挂起寄存器，偏移 `0x14`，在设备头文件中是 32 位成员。RM0008 用 `rc_w1` 标记有效挂起位，含义是软件可读，写 1 清除，写 0 对该位无作用。有效线号按具体芯片查表，保留位遵守手册要求。

| 某位的原挂起状态 | 写入该位 | 写后的状态（假设无新事件） |
| --- | ---: | ---: |
| 0 | 0 | 0 |
| 0 | 1 | 0 |
| 1 | 0 | 1 |
| 1 | 1 | 0 |


普通 RW 数据位通常用 0 和 1 保存状态。W1C 位把写入的 1 解释为清除请求。软件可以用 `pending & ~write_value` 推导写后的状态。硬件有新事件时，要结合事件与访问时序重新判断。

#### 6.2 逐行推导读出、写入和读回
假设 EXTI4、EXTI8、EXTI12 都挂起，读出 `0x1110`。目标是清 4、12，保留 8。清除掩码 `ack_mask = (1u << 4u) | (1u << 12u)`，也就是 `0x1010`。

| 步骤 | 错误的 `EXTI->PR &= ~ack_mask` | 正确的 `EXTI->PR = ack_mask` |
| --- | --- | --- |
| 写语句是否先读 PR | 读取 `0x00001110` | 直接写入 |
| CPU 准备的写入值 | `0x00001110 & 0xFFFFEFEF = 0x00000100` | `0x00001010` |
| 硬件处理的清除请求 | 只清 bit 8 | 清 bit 4、12 |
| 执行后再读 PR | `0x00001010` | `0x00000100` |


`0xFFFFEFEF` 只是反掩码。CPU 还要将它与读出的旧值按位与，才能得到真正写到总线上的数据。`EXTI->PR |= ack_mask` 也会先读旧值。本例中它算出 `0x1110 | 0x1010 = 0x1110`，会把三位都清掉。

前面的小例子可同样推导。bit 8、9 挂起时先读到 `0x0300`，错误的 `&= ~(1u << 8u)` 向 PR 写 `0x0200`，硬件清掉 bit 9，随后读回 `0x0100`。正确地只清 bit 8 时，应直接写 `0x0100`，随后读回 `0x0200`。

#### 6.3 共享中断入口里的用法
以 STM32F103 的 EXTI5～9 共享入口为例。若这段代码只处理 EXTI6，先检查本线路，再只清自己确认的位。

```c
const uint32_t line6 = UINT32_C(1) << 6u;
const uint32_t pending = EXTI->PR;

if ((pending & line6) != 0u) {
    EXTI->PR = line6;
    // 处理 EXTI6，或把工作交给主循环
}
```

这里读取 PR 是为了判断事件来源，写入 PR 是为了确认处理的线路。其余线路应由对应分支或代码处理。同一挂起位只能表达当前是否挂起，多次边沿可能合并成一个挂起状态。需要准确计数时，应另外考虑硬件捕获或计数方案。

### 七、把三类寄存器放在一起读
| 类型 | 代表 | 读取的含义 | 写入的含义 | 本节用法 |
| --- | --- | --- | --- | --- |
| 普通可读写数据 | GPIO ODR | 输出锁存状态 | 更新输出锁存值 | 整字写会更新全部有效位，单独改位用 BSRR |
| 写命令 | GPIO BSRR | 按手册的只写位规则处理 | 低位写 1 置位，高位写 1 复位 | 拼好两个掩码，直接写一次 |
| 可读、写 1 清零 | EXTI PR | 哪些线路挂起 | 写 1 请求清除对应标志 | 读取用于判断，直接写入确认掩码 |


碰到新寄存器时，依次确认**芯片型号和地址 → C 成员与允许访问宽度 → 有效位 → 每位访问属性 → 这条 C 代码会发出几次读写 → 硬件收到值后做什么**。遇到 `|=` 或 `&=`，先把读出值、运算值、总线写入值、写后读回值分别记下来。


## 四、工程应用与常见陷阱

1. 移位位数必须小于左操作数提升后的位宽，掩码要考虑 signed/unsigned 转换。
2. 不要仅凭 C 语言赋值语义推断外设寄存器操作：W1C、只读、写专用寄存器各不相同。
3. 使用不同 STM32 系列时，EXTI 挂起寄存器的清除机制与字段名称应重新核实参考手册。

1. `#define BAD(n) 1u << n`，`BAD(2+1)` 的实际展开会发生什么？

5. STM32 W1C 挂起寄存器已有 bit3 和 bit5 为 1，只想清 bit3，应该写什么？为什么不做普通读改写？

## 七、参考答案与解析（完成自检后再看）

**1.** 展开成 `1u << 2+1`，按优先级相当于 `1u << (2+1)`；仍应统一改成 `(1u << (n))` 以防放入其他表达式时出错。

**2.** 选中 a 分支时 i++ 可能被求值两次，应改用内联函数等安全方式。

**3.** 前者会，后者不会；ifdef 判断是否定义，if 判断数值。

**4.** 1u<<31 符合，1u<<32 的移位计数等于宽度，行为未定义。

**5.** 直接写对应 bit3 掩码（如 1u<<3），W1C 中写 1 表示清除；读改写可能将另一个已置位的挂起位一并清除。
