## 三、系统知识讲解与代码分析

### 3.1 C 语言基本数据类型
#### 3.1.1 整数类型与取值范围
在常见的 32 位 STM32、ESP32-S3 编译环境中：

| 类型 | 位宽 | 取值范围 |
| --- | :--- | :--- |
| `int8_t` | 8 | -128～127 |
| `uint8_t` | 8 | 0～255 |
| `int16_t` | 16 | -32768～32767 |
| `uint16_t` | 16 | 0～65535 |
| `int32_t` | 32 | -2147483648～2147483647 |
| `uint32_t` | 32 | 0～4294967295 |
| `int` | 32 | 通常与 int32_t 相同 |
| `unsigned int` | 32 | 通常与 uint32_t 相同 |


**注意：**

1. C 标准并不要求所有平台的 `int` 都是 32 位。
2. 某些 8 位、16 位 MCU 的 `int` 可能只有 16 位。
3. `char` 是有符号还是无符号，取决于具体实现。
4. `uint16_t` 等固定宽度整数类型在 `<stdint.h>` 中声明。
5. `sizeof` 的结果类型是 `size_t`，属于无符号整数类型。

对于嵌入式通信协议、寄存器数据和固定格式的数据结构，应优先考虑使用 `<stdint.h>` 中的固定宽度整数类型。

#### 3.1.2 sizeof 运算符
`sizeof` 用于获取类型或对象占用的存储空间，结果单位为字节。

```c
uint8_t  a = 10;
uint16_t b = 100;
uint32_t c = 1000;

sizeof(a); // 1
sizeof(b); // 2
sizeof(c); // 4
```

但需要注意：

```c
uint8_t a = 10;
uint8_t b = 20;

sizeof(a + b); // 通常为 4，而不是 1
```

因为 `a + b` 的表达式类型经过整数提升后是 `int`。

### 3.2 整数提升（Integer Promotion）
#### 3.2.1 什么是整数提升？
较小的整数类型参与某些运算时，会先转换为 `int` 或 `unsigned int`。

核心规则：

+ 如果 `int` 能表示原类型的所有值，提升为 `int`。
+ 否则提升为 `unsigned int`。

在当前 32 位 `int` 环境下：

| 原类型 | 整数提升后的类型 |
| --- | --- |
| `int8_t` | `int` |
| `uint8_t` | `int` |
| `int16_t` | `int` |
| `uint16_t` | `int` |
| `int32_t` | 通常仍为 `int` |
| `uint32_t` | 通常仍为 `unsigned int` |


重点：**即使原变量是无符号整数，提升后也可能变为有符号 `int`。**

#### 3.2.2 uint8_t 加法
```c
uint8_t a = 200;
uint8_t b = 100;

uint8_t c = a + b;
uint16_t d = a + b;
```

计算过程：

```text
uint8_t a = 200
uint8_t b = 100
       ↓ 整数提升
int 200 + int 100
       ↓
int 300
       ↓ 赋值转换
c = 44
d = 300
```

因为：

$
300\bmod256=44  
$
这里不是两个 8 位整数先发生了 8 位加法溢出，而是先以 `int` 类型计算，再转换为目标类型。

#### 3.2.3 uint16_t 加法
```c
uint16_t a = 50000;
uint16_t b = 20000;

uint16_t c = a + b;
uint32_t d = a + b;
```

两次加法表达式均以 `int` 类型计算：

```text
50000 + 20000 = 70000
```

最终：

```text
c = 4464
d = 70000
```

因为：

$
70000\bmod65536=4464  
$
**核心结论：等号左边的类型通常不决定右侧表达式使用什么类型计算。**

### 3.3 通常算术转换（Usual Arithmetic Conversions）
#### 3.3.1 基本原理
当两个不同整数类型的操作数参与加减乘除、比较等运算时，C 语言会根据整数提升与通常算术转换规则确定公共类型。

建议按以下顺序判断：

1. 确定两个操作数的原始类型。
2. 对需要提升的整数类型进行整数提升。
3. 根据有无符号性和整数转换等级确定公共类型。
4. 在公共类型下完成运算。
5. 如需赋值，再转换为目标类型。

对整数的公共类型选择规则，可以概括为：

+ 提升后类型相同：直接使用该类型。
+ 都是有符号或都是无符号：选择转换等级较高的类型。
+ 一有符号一无符号：先比较转换等级。
+ 若无符号类型等级不低于有符号类型：使用无符号类型。
+ 否则，若有符号类型能表示无符号类型的全部值：使用有符号类型。
+ 其余情况：使用与该有符号类型对应的无符号类型。

#### 3.3.2 int16_t 与 uint16_t 比较
```c
int16_t a = -1;
uint16_t b = 1;

int result = (a < b);
```

在 32 位 `int` 环境下，两个操作数均提升为 `int`。

比较：

```text
-1 < 1
```

结果：

```text
result = 1
```

#### 3.3.3 int32_t 与 uint32_t 比较
```c
int32_t a = -1;
uint32_t b = 1;

int result = (a < b);
```

在典型 STM32/ESP32 环境下，有符号操作数 `a` 转换为 `uint32_t`。

```text
-1 → 4294967295
```

最终比较：

```text
4294967295 < 1
```

结果：

```text
result = 0
```

**注意：并不是所有 signed 与 unsigned 混合运算，都会无条件转换为 unsigned。必须先分析整数提升和转换等级。**

#### 3.3.4 嵌入式工程实例：UART 长度判断
错误示例：

```c
int32_t received = -1;
uint32_t required = 8;

if (received >= required)
{
    // 错误：可能把负数当成很大的无符号数
}
```

更合理的写法：

```c
if (received < 0)
{
    // 处理错误
}
else if ((uint32_t)received >= required)
{
    // 数据足够
}
else
{
    // 数据不足
}
```

原则：

**先验证错误码和取值范围，再进行安全的类型转换。**

### 3.4 整数类型转换规则
#### 3.4.1 有符号转无符号
如果原值无法由目标无符号类型直接表示，按照模 (2^N) 规则转换，其中 N 是目标无符号整数的位数。

例如：

```c
int32_t a = -1;

uint8_t b = a;
uint16_t c = a;
uint32_t d = a;
```

结果：

```text
b = 255
c = 65535
d = 4294967295
```

公式：

$
\text{结果}=x\bmod2^N  
$
结果选取目标无符号整数可表示范围内的唯一余数。

这是 **C11 明确定义的行为**，不是未定义行为。

#### 3.4.2 无符号转有符号
如果原数值可以被目标有符号类型表示，转换后数值不变。

例如：

```c
uint16_t a = 100;
int16_t b = a;  // b = 100
```

如果原值无法表示：

```c
uint16_t raw = 65532;
int16_t value = raw;
```

按照 C11：

**转换结果是实现定义的，或者产生实现定义的信号。**

在典型 GCC 环境下：

```text
value = -4
```

但不能把 GCC 的具体行为直接当成所有 C11 实现都必须遵守的语言保证。

#### 3.4.3 整数转换规则总结
| 情况 | C11 规定 |
| --- | --- |
| 原值能由目标类型表示 | 数值不变 |
| 原值不能表示，目标为无符号 | 模 (2^N) 转换 |
| 原值不能表示，目标为有符号 | 实现定义的结果或信号 |

### 3.5 整数溢出与回绕
#### 3.5.1 无符号整数回绕
```c
uint32_t count = UINT32_MAX;

count++;
```

最终：

```text
count = 0
```

无符号整数运算遵循模 (2^N) 规则。

这是定义明确的行为。

再看：

```c
uint8_t count = 255;

count++;
```

在 32 位 `int` 环境下：

1. `count` 提升为 `int`。
2. 计算 `255 + 1 = 256`。
3. 赋值时转换成 `uint8_t`。
4. 得到 0。

虽然最终也发生回绕，但需要区分运算阶段与赋值转换阶段。

#### 3.5.2 有符号整数溢出
```c
int32_t count = INT32_MAX;

count++;
```

数学结果超过了 `int32_t` 的最大可表示值。

在 C11 中，这属于：

**未定义行为（Undefined Behavior，UB）。**

不能保证一定得到 `INT32_MIN`。

即使某个 MCU 的机器指令表现为二进制回绕，也不能由此推出 C 程序具有该语言保证。

#### 3.5.3 类型转换与算术溢出的区别
```c
uint16_t a = 50000;
uint16_t b = 50000;

uint32_t x = a * b;
uint32_t y = (uint32_t)a * b;
uint32_t z = (uint32_t)(a * b);
```

分析：

| 变量 | 计算方式 | 结果 |
| --- | --- | --- |
| x | int 乘法溢出 | 未定义行为 |
| y | uint32_t 乘法 | 2500000000 |
| z | 先 int 乘法溢出，后转换 | 未定义行为 |


为什么？

`uint16_t` 在本平台上先提升为 `int`。

因此：

```c
a * b
```

尝试得到：

```text
2500000000
```

但超过了 `INT32_MAX`，乘法阶段就已经发生未定义行为。

正确做法：

```c
uint32_t result = (uint32_t)a * b;
```

如果更大范围的运算结果可能超过 `uint32_t`，还应选用适当的更宽类型并执行范围检查。

**重点：强制类型转换必须放在运算之前，才能影响运算时使用的类型；运算之后再强转，无法补救已经发生的未定义行为。**

### 3.6 位运算与整数提升
#### 3.6.1 uint8_t 按位取反
```c
uint8_t status = 0xA0;

uint8_t value = ~status;
```

在典型 32 位二进制补码环境下：

```text
status       = 0xA0

提升为 int   = 0x000000A0

按位取反     = 0xFFFFFF5F

赋值给 uint8_t

value        = 0x5F
```

所以：

```c
value == 0x5F; // 真
```

但是：

```c
if (~status == 0x5F)
```

结果为假。

原因是 `~status` 的表达式类型为 `int`，不是 `uint8_t`。

在题设环境下：

```text
~status = -161
0x5F    = 95
```

因此比较不成立。

如果明确希望比较取反后的低 8 位结果：

```c
if ((uint8_t)(~status) == 0x5FU)
{
    // 条件成立
}
```

#### 3.6.2 MCU 寄存器位掩码
假设需要清除某个普通 32 位可读写寄存器值的第 5 位：

```c
uint32_t reg = 0xFFFFFFFFU;

reg &= ~(UINT32_C(1) << 5);
```

结果：

```text
reg = 0xFFFFFFDF
```

使用明确的无符号整数掩码，可以减少有符号运算带来的不必要风险。

注意：

+ 移位数量必须合法。
+ 不应对负数进行不符合规则的左移。
+ 实际寄存器可能具有写 1 清零等特殊行为。
+ 对硬件寄存器还需要结合 `volatile`、访问时序和芯片参考手册分析。

`volatile` 将在 1.3 章节重点学习。

### 3.7 传感器数据拼接与补码
#### 3.7.1 大端数据拼接
假设传感器返回：

```c
uint8_t buf[2] = {0xFF, 0xFC};
```

协议约定为大端格式：

```text
buf[0]：高字节 0xFF
buf[1]：低字节 0xFC
```

组合：

```c
uint16_t raw =
    ((uint16_t)buf[0] << 8) | buf[1];
```

结果：

```text
raw = 0xFFFC
raw = 65532
```

这里左移表达式中的 `uint16_t` 在常见 32 位 `int` 环境下仍会提升为 `int`，但 `0xFF << 8` 的结果在 `int` 可表示范围内，因此该操作是有效的。

#### 3.7.2 16 位二进制补码
如果传感器协议约定为有符号 16 位补码：

| 原始数据 | 对应有符号值 |
| --- | :--- |
| `0x0001` | 1 |
| `0x7FFF` | 32767 |
| `0x8000` | -32768 |
| `0xFFFE` | -2 |
| `0xFFFC` | -4 |
| `0xFFF8` | -8 |
| `0xFFFF` | -1 |


对于原始无符号值大于 32767 的情况：

$
\text{补码数值}=\text{raw}-65536  
$
例如：

```text
0xFFF8 = 65528

65528 - 65536 = -8
```

#### 3.7.3 避免依赖实现定义的转换
直接写：

```c
int16_t value = raw;
```

如果 `raw` 大于 32767，按照 C11 属于超范围转换到有符号类型，结果是实现定义的或产生实现定义的信号。

如果需要按照协议严格、可移植地解析二进制补码，可以先使用 `int32_t`：

```c
uint16_t raw =
    ((uint16_t)buf[0] << 8) | buf[1];

int32_t value;

if (raw <= INT16_MAX)
{
    value = (int32_t)raw;
}
else
{
    value = (int32_t)raw - 65536;
}
```

这样转换过程完全处于 `int32_t` 的有效范围内。

若需要最终保存到 `int16_t`，此时 `value` 的值已经确定在 -32768～32767 之间，可以再安全转换。

### 3.8 定义明确、实现定义与未定义行为
这三个概念必须严格区分。

#### 3.8.1 定义明确（Defined Behavior）
C 标准明确规定其行为或结果。

示例：

```c
uint32_t a = (uint32_t)-1;
```

结果：

```text
4294967295
```

#### 3.8.2 实现定义（Implementation-defined Behavior）
C 标准允许实现选择行为，并要求实现对该行为作出说明。

例如 C11 中：

```c
uint16_t raw = 65532;

int16_t value = raw;
```

由于数值超出目标有符号类型范围，其转换结果是实现定义的，或者产生实现定义的信号。

在典型 GCC 实现中结果为 -4。

#### 3.8.3 未定义行为（Undefined Behavior）
C 标准对程序行为不施加要求。

例如：

```c
int32_t a = INT32_MAX;

a++;
```

这是有符号整数算术溢出，属于未定义行为。

#### 3.8.4 对照表
| 场景 | 行为分类 |
| --- | --- |
| `(uint16_t)-8` | 定义明确 |
| `(int16_t)65528U` | C11 实现定义或实现定义的信号 |
| `uint32_t x = UINT32_MAX; x++;` | 定义明确 |
| `int32_t x = INT32_MAX; x++;` | 未定义行为 |
| `uint32_t x = (uint32_t)a * b;` | 在本章给定数值下定义明确 |
| `uint32_t x = a * b;` | 本章 50000×50000 示例中为未定义行为 |

### 3.9 工程开发建议
在 STM32、ESP32 项目中，建议遵守以下规则：

1. 与硬件协议相关的数据尽量使用固定宽度整数。
2. 混合 signed/unsigned 运算前，明确操作数类型。
3. 负数错误码先判断，再转换为无符号长度。
4. 乘法可能超出 `int` 范围时，在运算前提升到足够宽的类型。
5. 无符号整数回绕虽然有定义，也要判断业务逻辑是否允许。
6. 不依赖有符号整数溢出后的特定结果。
7. 解析传感器补码时区分协议数值与 C 语言类型转换。
8. 对位运算、移位操作明确计算位宽。
9. 开启合理的编译器警告，例如 `-Wall`、`-Wextra`、`-Wconversion`、`-Wsign-conversion`，并结合具体工程处理警告。
10. 对 ADC、通信协议和采样数据的范围进行边界测试。

## 四、工程应用与常见陷阱

1. UART 返回负数错误码时，先检查 <0，再与 size_t/uint32_t 长度比较。
2. 传感器大端原始数据先按字节拼成无符号数，再按协议规定解释补码，别直接依赖超范围转有符号。
3. 大整数乘法先提升操作数，如 (uint32_t)a * b；如果结果可能超出 uint32_t，改用更宽类型并检查范围。

## 五、个人易错点与复盘

### 5.1 本章易错点与个人复盘
以下是本次学习过程中实际出现过的问题，后续复习应重点检查。

#### 5.1.1 误认为 uint8_t 按 8 位直接计算
错误认识：两个 `uint8_t` 相加，直接在 8 位范围内计算。

正确理解：在当前 32 位 int 环境下，通常先提升为 `int`，再执行运算。

#### 5.1.2 误认为赋值目标决定运算类型
错误认识：

```c
uint32_t result = a * b;
```

由于 result 是 uint32_t，乘法也自动使用 uint32_t。

正确理解：右侧表达式先按照操作数的类型规则计算，然后才进行赋值转换。

#### 5.1.3 混淆 signed 与 unsigned 比较
错误认识：`-1 < 1` 总是成立。

正确理解：混合整数类型比较前，必须先进行整数提升和通常算术转换。

#### 5.1.4 混淆有符号算术溢出与类型转换
错误认识：只要一个数超出了目标类型范围，就属于未定义行为。

正确理解：

+ 转换到无符号类型：定义明确的模转换。
+ 转换到有符号类型且超范围：C11 实现定义的结果或信号。
+ 有符号整数算术运算超出结果类型范围：未定义行为。

#### 5.1.5 补码换算容易出现偏差
```text
0xFFFE = -2
0xFFFC = -4
0xFFF8 = -8
```

对于 16 位补码，负值可以使用：

```text
无符号值 - 65536
```

但要注意，这是协议数值解释规则，不能直接代替 C11 的有符号超范围转换规则。

#### 5.1.6 混淆高字节和低字节
大端格式：

```text
高字节在前
低字节在后
```

例如：

```text
buf[0] = 0xFF
buf[1] = 0xFE

组合结果 = 0xFFFE
```

不是 `0xFEFF`。

#### 5.1.7 忽略位运算前的整数提升
```c
uint8_t value = ~status;
```

不能认为 `~status` 一定只操作 8 位。

需要分析整数提升后的表达式类型。
