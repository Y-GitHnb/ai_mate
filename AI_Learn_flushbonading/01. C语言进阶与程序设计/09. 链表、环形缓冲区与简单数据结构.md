## 二、数组、栈和队列描述的是不同层面
| 概念 | 描述什么 | 工程示例 |
| --- | --- | --- |
| 数组 | 同类型元素连续存放，通过下标访问 | 采样值数组、固定设备地址表 |
| 栈 | 后进先出，LIFO | 暂存嵌套解析状态，最后进入的状态先恢复 |
| 队列 | 先进先出，FIFO | 按到达顺序处理 UART 字节 |
| 单链表 | 节点通过指针连接，可以调整遍历顺序 | 可增删的设备轮询表 |
| 环形缓冲区 | 用回绕的读写位置复用固定存储空间 | 用数组实现 FIFO 字节队列 |


数组回答**元素放在哪里**。栈和队列回答**下一次取哪个元素**。同样一段数组，维护栈顶位置可以实现栈，维护循环推进的读写下标可以实现 FIFO 队列。

例如从数组中实现一个简单队列，每取走第 0 个元素就把其余元素前移，逻辑容易理解，但取一次可能要搬动许多数据。环形缓冲区通过移动下标完成同样的取出操作，仍在排队的数据可以留在原来的内存位置。

## 三、单链表
### 3.1 节点、头指针与内存关系
一个链表节点通常包含两部分：

+ **业务数据**，例如一个 I?C 设备地址。
+ **链接成员**，例如 `next`，保存下一个节点的地址。

`head` 是独立的指针变量，保存首节点地址。`head == NULL` 表示空链表。节点的 `next == NULL` 表示它是尾节点。

假设设备轮询顺序为 `imu → env → current`，内存关系可以表示成下面的表格。表中的 `&imu` 等表示对象地址，物理位置可以各不相邻。

| 存储位置 | 业务数据 | 存着哪个地址 |
| --- | --- | --- |
| 变量 `head` | 无 | `&imu` |
| 对象 `imu` | `0x68` | `imu.next = &env` |
| 对象 `env` | `0x76` | `env.next = &current` |
| 对象 `current` | `0x40` | `current.next = NULL` |


`struct PollNode *next` 可以写在 `struct PollNode` 定义内部。此时结构体类型尚未定义完整，但可以声明指向它的指针。按链表遍历时，CPU 从当前节点读出 `next`，再访问下一节点。数组则可以根据基地址、下标和元素大小直接定位。

### 3.2 插入时先保存旧后继
初始顺序为 `imu → current`，要把 `env` 插到 `imu` 后面。

| 步骤 | `imu.next` | `env.next` |
| --- | --- | --- |
| 插入前 | `&current` | `NULL` |
| 执行 `env.next = imu.next` | `&current` | `&current` |
| 执行 `imu.next = &env` | `&env` | `&current` |


若把两句调换，第二句读到的 `imu.next` 已经变成 `&env`，于是 `env.next` 指向自己。从 `head` 遍历会一直停留在这个环里。

如果明确知道旧后继就是 `current`，写 `imu.next = &env;` 后再写 `env.next = &current;`，在本节的单执行上下文中也能得到相同的最终链接。通用插入函数读取前驱的实际 `next`，因此前驱原来的后继是其他节点或 `NULL` 时也能工作。

### 3.3 摘除中间节点与首节点
| 情况 | 先修改什么 | 再做什么 |
| --- | --- | --- |
| 摘除中间节点 `env` | `imu.next = env.next;` | `env.next = NULL;` |
| 摘除首节点 `imu` | `head = imu.next;` | `imu.next = NULL;` |


中间节点有前驱，改前驱的 `next` 即可。首节点通过 `head` 进入，摘首节点时要改 `head` 本身。`head->next` 则是首节点对象的成员。

如果把更新头指针封装进函数，调用时传入 `&head`。形参类型为 `PollNode **`，函数里的 `*head` 就是调用者的头指针变量，可以直接赋值。

### 3.4 完整 C 示例：设备轮询表
三个设备地址仅供示例。程序用打印地址模拟轮询，并验证插入、摘除中间节点和摘除首节点。节点都在 `main()` 中创建并使用，寿命覆盖整个示例。

```c
#include <assert.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

typedef struct PollNode {
    uint8_t addr7;
    struct PollNode *next;
} PollNode;

/* prev 指向链中的有效节点，node 尚未挂入链表。 */
static void insert_after(PollNode *prev, PollNode *node)
{
    node->next = prev->next;
    prev->next = node;
}

/* prev 指向链中的有效节点。没有后继时返回 NULL。 */
static PollNode *detach_after(PollNode *prev)
{
    PollNode *node = prev->next;

    if (node == NULL) {
        return NULL;
    }

    prev->next = node->next;
    node->next = NULL;
    return node;
}

/* head 指向调用者的头指针变量。 */
static PollNode *detach_head(PollNode **head)
{
    PollNode *node = *head;

    if (node == NULL) {
        return NULL;
    }

    *head = node->next;
    node->next = NULL;
    return node;
}

int main(void)
{
    PollNode current = {.addr7 = 0x40u, .next = NULL};
    PollNode imu = {.addr7 = 0x68u, .next = &current};
    PollNode env = {.addr7 = 0x76u, .next = NULL};
    PollNode *head = &imu;

    insert_after(&imu, &env);

    for (const PollNode *p = head; p != NULL; p = p->next) {
        printf("poll 0x%02X\n", (unsigned)p->addr7);
    }

    PollNode *removed = detach_after(&imu);
    assert(removed == &env && removed->next == NULL);
    assert(imu.next == &current);

    insert_after(&imu, removed);
    removed = detach_head(&head);
    assert(removed == &imu && removed->next == NULL);
    assert(head == &env && env.next == &current);
    return 0;
}
```

按 C11 编译示例，轮询输出依次为 `0x68`、`0x76`、`0x40`。摘掉 `env` 后，`imu` 重新接到 `current`。把 `env` 插回再摘掉 `imu`，头指针就指向 `env`，轮询顺序变为 `env → current`。

### 3.5 节点寿命、复杂度与工程选择
+ 摘除只改变链接。静态节点仍可重新挂入链表。动态申请的节点在摘除后，应由负责其所有权的一方决定何时释放。
+ 普通局部节点只在所属作用域的对象寿命内有效。如果轮询表要在初始化函数返回后继续使用，节点可放在模块静态存储中，或由寿命足够长的对象持有。
+ 已知前驱时，插入和摘除为 `O(1)`。如果只知道设备地址，要先逐个寻找，最坏为 `O(n)`。
+ 设备集合和顺序固定时，数组通常更直接。需要运行时注册、摘除或重新排序时，才有必要权衡链表的指针开销和遍历成本。
+ 如果另一个执行上下文会同时遍历或修改链表，必须先确定同步策略。本例的两步更新建立在单一执行上下文上。

## 四、环形缓冲区
### 4.1 数组布局与两个下标
以 `uint8_t data[8]` 为例，数据数组占 8 字节，有效下标是 `0～7`。缓冲区结构体还包含读写下标，其总大小应以 `sizeof(RingBuffer)` 为准。

+ `read_idx` 指向下一次要读的位置。
+ `write_idx` 指向下一次尝试写入的位置。
+ 成功读写后，对应下标推进。`(idx + 1) % N` 让最后一格的下一位置回到 0。

`read_idx = 6`、`write_idx = 1` 时，从读位置开始沿环走，到写位置之前的字节属于队列。假设它们依次为 A、B、C：

| 数组下标 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 当前待取数据 | C | — | — | — | — | — | A | B |
| 下标含义 |  | 下一次尝试写 |  |  |  |  | 下一次读 |  |


FIFO 取出顺序是 `data[6] → data[7] → data[0]`。表中的 `—` 表示该格当前不属于队列，其中可能还留有旧值。

### 4.2 为什么保留一个空槽
如果只用两个回绕下标，空时两个下标相等，写满整整一圈后也会相等。留空槽方案通过限制可用容量来区分这两种状态。

| 状态 | 判断方式 |
| --- | --- |
| 空 | `read_idx == write_idx` |
| 满 | `next(write_idx) == read_idx` |
| 可用总容量 | `N - 1` 个元素 |


在前例中，8 格实际可存 7 字节，已存 3 字节，还能写入 4 字节，分别写到 `1、2、3、4`。写完 `data[4]` 后，`write_idx` 变成 5。下一次尝试写时，`next(5) == 6`，与 `read_idx` 相等，因此 `data[5]` 留空。

可用公式推导已存元素数：

```c
used = (write_idx + N - read_idx) % N;
```

这个公式用于本节的回绕下标设计，且中间运算需使用足够宽的整数。保留空槽的位置会随着下标移动。若需要用满全部 N 格，还可以额外保存计数或满标记，并为共享状态设计相应的更新规则。

### 4.3 完整 C 示例：固定长度字节队列
这个实现采用**留一格、满时拒绝新数据**。下标使用 `size_t`，与数组索引和容量的类型一致。调用方提供有效的缓冲区地址，`out` 指向可写的 `uint8_t`。基本函数在单一执行上下文中使用。

```c
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

enum { RING_SLOTS = 8 };

typedef struct {
    uint8_t data[RING_SLOTS];
    size_t read_idx;
    size_t write_idx;
} RingBuffer;

static size_t next_idx(size_t idx)
{
    return (idx + 1u) % RING_SLOTS;
}

static bool ring_push(RingBuffer *rb, uint8_t byte)
{
    size_t next = next_idx(rb->write_idx);

    if (next == rb->read_idx) {
        return false;
    }

    rb->data[rb->write_idx] = byte;
    rb->write_idx = next;
    return true;
}

static bool ring_pop(RingBuffer *rb, uint8_t *out)
{
    if (rb->read_idx == rb->write_idx) {
        return false;
    }

    *out = rb->data[rb->read_idx];
    rb->read_idx = next_idx(rb->read_idx);
    return true;
}

int main(void)
{
    RingBuffer rb = {0};
    uint8_t byte = 0xFFu;

    if (ring_pop(&rb, &byte) || byte != 0xFFu) {
        return 1;
    }

    for (uint8_t i = 0; i < 7u; ++i) {
        if (!ring_push(&rb, i)) {
            return 1;
        }
    }
    if (ring_push(&rb, 0xFFu)) {
        return 1;
    }

    for (uint8_t i = 0; i < 2u; ++i) {
        if (!ring_pop(&rb, &byte) || byte != i) {
            return 1;
        }
    }
    if (!ring_push(&rb, 7u) || !ring_push(&rb, 8u)) {
        return 1;
    }

    for (uint8_t i = 2u; i <= 8u; ++i) {
        if (!ring_pop(&rb, &byte) || byte != i) {
            return 1;
        }
    }
    if (ring_pop(&rb, &byte)) {
        return 1;
    }

    puts("ring buffer OK");
    return 0;
}
```

| 程序执行位置 | `read_idx` | `write_idx` | 待取值，按 FIFO 排列 |
| --- | ---: | ---: | --- |
| 初始化后 | 0 | 0 | 空 |
| 写入 `0～6` 后 | 0 | 7 | `0, 1, 2, 3, 4, 5, 6` |
| 读出 `0` 和 `1` 后 | 2 | 7 | `2, 3, 4, 5, 6` |
| 写入 `7` 和 `8` 后 | 2 | 1 | `2, 3, 4, 5, 6, 7, 8` |
| 全部读完后 | 1 | 1 | 空 |


写入 `7` 的槽位是 `data[7]`，写入 `8` 的槽位是 `data[0]`，证明回绕后仍保持 FIFO 顺序。`push` 先写数据，再推进写下标。`pop` 先取数据，再推进读下标。满时写失败，原队列保持不变。空时读失败，`*out` 保持原值。`0x00` 本身可以是有效数据，空与满都由下标判断。

## 五、UART 接收工程
### 5.1 接收、暂存与协议解析
![](https://cdn.nlark.com/yuque/__mermaid_v3/188e9763880a25c801f201e5ab1d8076.svg)

UART 送来的是字节流，软件缓冲区负责保持顺序。AT 解析器根据协议识别行边界。例如本次取到 `\r\nO`，下次才取到 `K\r\n`，仍能拼成完整的 `OK` 行。只收到半行时，可以保存已收到的部分等待后续。如果已经确认有丢字节，应把当前响应标为可能损坏，并依据协议重新同步。

### 5.2 STM32F103：UART 中断写，主循环读
本例假设 STM32F103 单核裸机，只有 UART 中断执行 `ring_push()`，只有主循环取出字节，没有其他代码访问这份队列。下面复用前面的 `RingBuffer` 和 `ring_pop()`，由设备头文件提供 CMSIS 接口。

```c
static RingBuffer uart_rx = {0};

static bool uart_rx_pop(uint8_t *out)
{
    uint32_t saved = __get_PRIMASK();
    __disable_irq();

    bool ok = ring_pop(&uart_rx, out);

    __set_PRIMASK(saved);
    return ok;
}
```

屏蔽可屏蔽中断期间，主循环可以完成一次判空、取字节和推进读下标。恢复保存的 `PRIMASK`，就能保留调用前的中断状态。协议解析在函数返回后进行。`volatile` 不会把这几个步骤合并成一个原子动作。涉及 DMA、RTOS 或多核时，要重新确认有哪些执行者会读写数据和下标，再选择相应的同步机制。

### 5.3 ESP32-S3：使用 ESP-IDF v5.5.4 的 UART 驱动
`uart_driver_install()` 可以配置驱动的 RX 环形缓冲区和 UART 事件队列。应用任务用 `uart_read_bytes()` 取出驱动已经缓存的字节。假设端口、引脚和驱动已配置完成：

```c
uint8_t chunk[32];
int n = uart_read_bytes(UART_NUM_1, chunk, sizeof chunk, 0);

if (n > 0) {
    at_parser_feed(chunk, (size_t)n);  // 由项目实现
}
```

这里最后一个参数为 0，表示本次不等待。`n > 0` 时只处理前 `n` 个有效字节，`n == 0` 表示本次没读到数据，`n < 0` 走错误处理。即使单次读了多个字节，也仍需由解析器确定行或帧边界。应用如果直接使用驱动提供的 RX 缓冲区，可以根据协议需要决定是否再设一层暂存。

### 5.4 按接收速率估算容量
假设 UART 为 `115200、8N1`，每个数据字节在线上消耗 1 个起始位、8 个数据位和 1 个停止位。连续发送时，每秒约有 `115200 ÷ 10 = 11520` 个字节。

假设主循环 5 ms 不读，而接收中断在此期间正常入队，起点没有额外待转移的硬件积压。按任意到达相位估算，这段时间最多完成约 `ceil(11520 × 0.005) = 58` 个新字节。

| 容量项 | 字节数 |
| --- | ---: |
| 数组槽位数 | 64 |
| 保留空槽 | 1 |
| 实际可存容量 | 63 |
| 停读开始前已有积压 | 10 |
| 剩余可用 | 53 |
| 期间新到达 | 58 |
| 成功入队 / 入队失败 | 53 / 5 |


如果要求这组条件下的 58 个新字节全部存下，按留空槽方案，至少需要 `10 + 58 + 1 = 69` 个槽位。工程中还要用实际最长停读时间和积压测量验证估算。

### 5.5 硬件过载、软件队列满与分批到达
| 现象 | 所在层 | 说明 |
| --- | --- | --- |
| STM32F103 的 `ORE` 置位 | USART 硬件接收侧 | 新数据到达时，前一数据还没及时从接收数据寄存器取走。该标志说明至少丢了一个数据 |
| 本例 `ring_push()` 返回 `false` | 软件环形缓冲区 | 字节已被接收代码取出，但软件队列没有空间 |
| AT 解析器只有半行 | 协议解析层 | 可能只是分批到达，应结合接收错误和协议边界判断 |


`ring_push()` 每失败一次，可以记录一个软件入队失败的字节。`ORE` 是硬件状态标志，单凭一次置位无法得出精确的丢字节数量。如果出现 `ORE`，应优先检查硬件接收数据为何没有及时取走，例如中断响应太晚或屏蔽时间太长。扩大软件缓冲区有助于容纳已经取出的字节，硬件接收侧仍要及时服务。

ESP-IDF 的 `UART_FIFO_OVF` 对应硬件 RX FIFO 溢出，`UART_BUFFER_FULL` 对应驱动 RX 环形缓冲区已满。这两类事件可帮助判断先检查哪一段。

## 六、个人易错点
1. **头指针和节点成员**。`head` 是指针，`head.next` 不能访问成员。`head->next` 可以访问首节点的成员，但摘掉首节点需要写 `head = imu.next;`。
2. **插入顺序**。先取得旧后继，再修改前驱。反过来使用 `imu.next` 时，读到的可能已是新节点地址，导致自环。
3. **写下标和最后写入的槽位**。写完 `data[4]` 才推进到 `write_idx = 5`。若此时判满，`data[5]` 仍是空槽。
4. **串口收到和软件成功入队**。64 格、已积压 10 字节时，题设的 58 个字节都已被接收代码取出，其中 53 个成功入队，5 次入队失败。
5. **硬件过载与缓冲区容量**。判断 `ORE` 时先检查硬件数据有没有被及时取走。判断软件队列满时再计算容量和消费速度。

## 七、复习自检
1. 当前 `head → A → B → C`。要摘掉 A 并清除 A 的链接，应该修改哪些变量或成员？为什么需要先更新头指针？
2. 环形缓冲区有 8 格，保留 1 格。`read_idx = 5`、`write_idx = 2`。先读一次，再尝试写四次。实际读写了哪些槽位？最后两个下标是什么？
3. 64 格数组采用留空槽策略，已有 10 字节，停读期间到来 58 字节。多少次入队成功？在相同假设下，想全部存下至少需要多少槽位？
4. 测试时 `ORE` 出现过，但 `ring_push()` 从未失败。应该从哪一层排查？为什么？

参考答案：

1. 先写 `head = A.next;`，再写 `A.next = NULL;`。先断开 A 会丢掉用于更新头指针的后继地址。
2. 读 `data[5]`，写 `data[2]`、`data[3]`、`data[4]`。第 4 次写入失败。最终 `read_idx = 6`、`write_idx = 5`。
3. 成功 `63 - 10 = 53` 次，失败 5 次。全部存下至少需要 `10 + 58 + 1 = 69` 格。
4. 先检查 UART 硬件接收数据能否及时被读取。`ORE` 指向硬件接收过载，数据可能在进入软件队列前已经丢失。

## 八、本节小结
画链表时，从 `head` 出发区分**指针变量、对象和对象中的 **`next`。算环形缓冲区时，先写清**下标含义和空满策略**，再按实际写入位置逐步推进。排查 UART 时，沿**硬件接收、软件入队、协议解析**逐段确认数据在哪一步发生变化。
